# Exactory 0.85.1

This release lets the Codex reviewer routes verify the input of Codex CLI 0.167.0, and it makes
`problem-candidate-transfer` refuse an unresolvable destination on every supported Python. It follows 0.85.0. The
audit and the repair of the Codex routes are recorded in
`misc/harness-improvement/20261110050252-codex-transport-rejects-cli-0-167-developer-input` of the exactory
repository; the transfer fix is recorded in `misc/harness-improvement/20261109153246-abc-type-conjecture-creation`.

## Why

CI of 0.85.0 failed on Python 3.14 in one test: `problem-candidate-transfer` accepted a destination that is a
symbolic-link loop. The command resolved the destination with `Path.resolve()` and refused only when that call
raised. Since Python 3.13, a non-strict `resolve()` raises nothing for a loop
(https://docs.python.org/3.14/library/pathlib.html#pathlib.Path.resolve: "Changed in version 3.13: Symlink loops
are treated like other errors: OSError is raised in strict mode, and no exception is raised in non-strict mode").
The same command passed on Python 3.9 and 3.12.

With Codex CLI 0.167.0 installed, two result reviews on a `codex_cli_v1` route completed with a full answer, and the
transport marked both inputs unverified with `unknown_developer_input` and `unknown_or_tool_input`. The transport
accepted only the startup inputs that it had audited for Codex 0.159.2 and 0.162.1. A record whose reviewer route is a
Codex route could not obtain a verified review with this CLI.

The audit read the rollouts of both reviews. Codex 0.167.0 writes two startup inputs that 0.162.1 did not write:

- An `additional_tools` item with the model's tool list: the `functions`, `clock` and `collaboration` namespaces. The
  list is the same in both reviews and holds no path, memory, plugin, app or MCP server. Sessions that load user
  configuration get a different list with two more namespaces, so the list is accepted only by its digest.
- A developer message whose text is the review instructions of the request. Its digest changes with the
  instructions, so it is not a fixed declaration. It is accepted only when its text is exactly the instructions of
  the request.

The other three developer messages are byte-identical to the audited declarations of 0.162.1.

## What changed

- `problem-candidate-transfer` resolves the destination in strict mode. A destination that does not exist is refused
  with `invalid_input` and the message "destination_workspace does not exist. ...", and a destination that cannot be
  resolved, a symbolic-link loop included, with `invalid_input` and the message "destination_workspace cannot be
  resolved. ...", with the same code and message on Python 3.9, 3.12, 3.13 and 3.14. A transfer names a record that
  already took the candidate up, so its workspace exists. The command now checks the slate before the destination,
  so a candidate that the latest slate does not list is `problem_candidate_transfer_not_on_slate` whatever the
  destination. The skill and the CLI reference say that the path must exist.
- `codex_cli_v1`, `codex_cli_framed_v1` and `codex_cli_visual_v1` accept the startup inputs of Codex 0.167.0 as a new
  audited set: the tool list with the digest `a066e4e81a2d3e62b1ac3cd628a56afce8ff553b858fa78cb294ea87bfcfe68d`, the
  instructions message, and the three declarations of 0.162.1, in this order.
- An `additional_tools` item counts only with the role `developer`, a list of tools, and a place before the packet.
  Another shape stays `unknown_or_tool_input`. A tool list after the packet is `late_developer_input`. A tool list
  with another digest, a 0.162.1 sequence with a tool list, a 0.167.0 sequence without one, other instructions and
  one more developer message stay `unknown_developer_input`.
- `docs/research-decisions.md` names Codex CLI 0.167.0 in the startup contract of the Codex route.

## What stays the same

- A rollout of Codex 0.159.2 or 0.162.1 verifies as before. A replay of the audited 0.162.1 rollout gives the same
  evidence object as 0.85.0.
- The tool list is never part of the packet comparison. A call of any tool is still caught as `tool_call:<name>` or
  `unknown_or_tool_input`.
- No control, environment check, packet check or output check changes.

## What stored records see

- The bytes of `research_harness/review_codex_transport.py`, `research_harness/review_codex_framed_transport.py` and
  `research_harness/review_codex_visual_transport.py` changed. A Codex route pins the SHA-256 of its transport in its
  runtime, so every `codex_cli_v1`, `codex_cli_framed_v1` and `codex_cli_visual_v1` route recorded before 0.85.1
  needs a new probe before its next review. A run or a probe on such a route is refused with
  `review_route_runtime_stale`. The stale-route procedure of the route instructions applies: record a new route with
  a new id and the same adapter, model, endpoint and configuration, probe it, and assign the role again on it, or,
  for a slot with history, retire the stale route and continue the slot through a context repair.
- Recorded probes and reviews keep their standing. They verify against the runtime that their route pinned.
- The two unverified reviews that found the defect stay unverified. Their responses pin the runtime of 0.85.0.
- A candidate transfer that 0.85.0 recorded keeps its bytes and its standing, also when its destination did not
  exist.
- No migration is necessary.

## Known limits

- The audit covers two text reviews on `codex_cli_v1`. No `codex_cli_framed_v1` or `codex_cli_visual_v1` rollout of
  Codex 0.167.0 was read. Those routes accept the same audited set; if Codex gives them another tool list, their
  input stays unverified until that list is audited.
- The tool list offers `exec` and the collaboration tools although the route sets the code-mode and multi-agent
  features to false. This was already so on Codex 0.163.0; 0.167.0 now writes the list to the rollout. Any call is
  caught.
