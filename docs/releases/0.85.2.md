# Exactory 0.85.2

This release makes a command report a local tool that did not finish within its own time limit, instead of ending
with a traceback. It follows 0.85.1. The failure, the decision and the measurement are recorded in
`misc/harness-improvement/20261110164908-record-check-crashes-on-pdf-render-timeout` of the exactory repository.

## Why

The comparison of 0.84.0 and the stage C code of 0.85.0 ran `record-check` on a clone of a live math-conjecturer
record while other comparisons and two test suites ran on the same machine. One run ended with a traceback after
699 seconds. The harness renders the pages of a native PDF that a review cites with `pdftoppm`, and gives each page 60
seconds. Page 39 did not finish in that time, and `subprocess.run` raised `subprocess.TimeoutExpired`. That exception
is not one of the harness's typed errors, so it ended the isolated child of `record-check`, and the command printed
a traceback and no report. A test showed that `status`, `next` and `gate post` on such a record ended the same way.

## What changed

- A command now ends with the code `local_tool_timeout` when a local tool does not finish within its time limit. The
  details give `tool` and `budget_seconds`, and the message says that the run decided nothing about the record and
  that the command can run again when the machine has less load. The error is a JSON error, and the exit status is 1.
  This holds for `exactory-research`, `exactory`, `exactory-draft` and `exactory-lab`.
- In `record-check`, the step that reached the tool fails with `local_tool_timeout`, in the same row shape as
  `record_command_timeout`. The report says `ready` false, and the command exits with status 1. The isolated child
  now writes its report.
- The conversion happens only at the command boundary. Below it, the timeout passes every validator unchanged, so an
  unfinished render never makes a review mismatched, refused or unauthenticated, records no refusal, and is not
  cached. The next run renders the page again, and a review whose render finishes keeps its standing.
- `docs/research-cli.md` describes local tool limits in the section on `record-check`.

## What stays the same

- The 60-second limit of a page render. On 2026-11-10, page 39 of the two PDFs of the record that failed took 0.38 to
  0.40 seconds alone, up to 5.41 seconds beside 36 busy processes, and 8.61 seconds at a load average of 64. The
  worst measured time is about one seventh of the limit, so a longer limit has no measured basis. The cause of the
  live timeout is not established; memory pressure during the comparison is an assumption, and a measurement of
  render time with memory pressure recorded during a full comparison would test it.
- No file that a reviewer route pins changes, so no route becomes stale. `research_harness/review_pdf_pages.py`
  keeps its bytes.
- No record, review, gate or obligation changes. A run in which every tool finishes gives the same output as 0.85.1.

## What stored records see

- Nothing changes in a stored record. No migration is necessary.

## Known limits

- Only the `exactory-research` paths were reproduced in a test. The wrapper of `exactory`, `exactory-draft` and
  `exactory-lab` covers the same calls, which these commands reach through their imports.
- The command does not retry the tool. A user who sees `local_tool_timeout` runs the command again.
