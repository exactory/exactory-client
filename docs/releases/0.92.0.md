# Exactory 0.92.0

This release repairs how the harness plans and starts reviewer calls, and what a later openness chain keeps from
an earlier chain. The release also puts new forms of a
review into the plugin (the session rules v4, the parts protocol v3, the math protocol v2 and a final in pages).
No command selects these forms yet. The release follows 0.91.14.

## What changed

### Reviewer calls and route records

- A plan names a route record that takes its command. Before, a plan of `review-series` or `next` sometimes named a
  route record that refuses the planned command: a record that pins another reviewer runtime than the installed
  one, or a retired record. Now each completed plan goes through one rule
  (`research_harness/review_route_plan.py`). A step that starts new work names a verified route record with the
  same adapter, model, endpoint and configuration that pins the installed runtime. If the store has no such record,
  the plan says what is missing.
- A retired route record keeps the state of its latest probe that has an answer. Before, a probe that failed
  without an answer left a retired route record unverified, also after the reviewer runtime changed. Carried
  reading turns were then not ready, and a new chain read every text again.
- A recorded page manifest verifies under the renderer profile that it recorded. Before, a stored review on a
  visual route lost its authentication after an update of the PDF renderer, or on a machine without the renderer.
  Now the harness verifies such a manifest from the stored page images. New reviewer work on a visual route still
  needs the renderer that its manifests record. Without that renderer the command refuses with
  `review_visual_source_mismatch` before it renders a page.
- A reviewer call reads the context that the review records give at the time of the call. Before, `review-run` read
  only the context that the assignment recorded. A failed probe of the route record of a turn did not stop a call
  that an agent gave directly. A contamination event on a turn of the review did not stop it. Now four commands
  read the state of the route record and the contamination events of each turn. These commands are `review-run`,
  the dispatch of a staged task, `review-output-correction`, and `review-assignment` for the next turn of a v7 or
  math reading chain. If a turn has no verified context, the command sends no request and records nothing. It
  refuses with `review_context_unverified` or `review_context_contaminated`. The details name the turn
  (`details.turn`) and the plan of the head (`details.next`). `review-series` gives the same code as a handoff with
  its step. "Effects and limits" lists the cases where that step is not correct.
- The documented steps let two bars run at the same time. The default capacity policy permits one reviewer call
  at a time in a store. Before, no step told a session to record a policy for two routes, so two bars ran one
  after the other. Now `next` names the bar assignment for a record that needs its two bars. If the store has the
  default policy and at least two verified route records of covered adapters, that step holds the member
  `scheduler`. The member gives one call to each of those routes. A plan that waits for the store limit says how to
  record its suggested scheduler.

### Openness chains

- A later chain keeps the readings of the units that did not change. Before, a selection of carried readings read
  each earlier chain against the content records of the present. Two changes that commands write made the
  observer of an earlier chain refuse every prefix: a bundle that names a delivered capture as a supplement, and
  the first fetched copy of a work whose text was supplied with `import-fulltext`. A later chain then carried no
  turn and read every text again. Now a new first assignment stores its selection as
  `exactory-openness-carried-selection-v3`. This selection reads each earlier chain against the content records
  as they were when that chain started. A stored selection of version 1 or 2 keeps its rule.
- A new problem openness chain records a finding of version 2. The prompt states when literature that the record
  names as not reached is a limit of a `supported_open` finding and when it blocks the finding. A ground of the
  kind `reviewer_gap` holds the fields of a named gap.
- A v7 chain accepts a packet with a large finding index. Values other than `queries` leave the index, the
  largest first, and the index names each of them by the handle of its unit. The reading turns of the chain
  deliver the values that a final names.

### New forms of a review, in the plugin and not selected

The plugin holds four new forms. Each form is selected by one constant, and each constant keeps its value of
0.91.14. So every new review starts in the form that 0.91.14 uses.

| Form | What it is | Constant |
| --- | --- | --- |
| Session rules v4 | A bar, slate or result review in turns with a capacity plan, with a final in one request or in pages | `NEW_SESSION_RULES` |
| Parts protocol v3 | A series for a review whose single request does not fit its route | `NEW_SERIES_PROTOCOLS` |
| Math protocol v2 | A math reading chain that carries earlier turns | `NEW_MATH_CHAIN_PROTOCOLS` |
| A v7 final in pages | The final of an openness chain in page turns and a closing turn | `V7_FINAL_FORMS` |

This release also holds repairs of these forms. A turn of a v4 session holds the instructions of its role. A
study review states the accepted forms of an evidence entry. A recorded v4 review has a refresh step.
Independent reviews and the checks of the prompt texts found more defects in these forms on 2026-11-21. Among
them: a page answer with a wrong list index passes its page, and the closing turn then cannot repair the final.
The forms stay unselected until these defects are repaired.

### Messages and documents

- The refusal and handoff messages of the changes above state the condition, the members of `details` and the
  step. The CLI reference and the skills state the same steps. A handoff for a stale or a retired route record
  names the command of `details.step`, the step that the plan of the head names.

### The guards and the tools of the repository

- The capacity guard covers the packets of the new forms. Each member of a packet declaration has a class and a
  bound, the admission of its request, or the stop of its chain. No member keeps the bound `open`. The packet
  registry declares the accounts of a stored value in one definition. The source inventory compares that
  definition with the member table of the validator.
- The continuity guard drives the new forms in each size class. It names six known defects of these forms in its
  table `FORM_DEFECTS`.
- `ci/must_pass.py run` runs the tests in the groups of the CI shards and reports the time of each test. If the
  set of a change holds more than 7% of the test modules, the command runs the near part and names the far part.
  The full suite of the CI is the check of the far part.
- `ci/core_operation_cost.py` measures `open`, `status` and one write on a copy of a record, beside the budgets of
  `ci/budgets.json`.
- A test module that holds a test of more than 300 s has a fixed CI shard. Before, an added test moved such a
  test into the shard of the largest fixture, and one job reached its limit of 180 minutes.
- The incident ledger gains 52 entries.

## Not in this release

This work of the release plan is not in 0.92.0. The next release effort carries it.

- The switch that selects the new forms, and the confirmation runs with the new forms.
- A slate that starts as a series when its request does not fit its route. A slate with a large forming import
  still ends with `review_route_capacity_below_floor`, as in 0.91.14.
- The repairs of six defects that the continuity guard found in the new forms.
- The repairs of the defects that the checks of the prompt texts found, and the final prompt texts of the new
  forms.
- The steps of a capacity stop of a context repair. In 0.91.14 and in this release, such a stop can name the
  retirement of the route record that serves the repair.
- The stop of a chain whose own unit changed, and the bound of the notes in the prompt of a v7 reading turn.
- A shorter write lock for a store with a long history. The design is reviewed, and the measurement on the
  largest live store is not done.
- The faster render after a write, the audit of payloads with a wrong shape, and the open checks of 0.91.11 to
  0.91.14.
- The check of a citation when a record takes it. In this release, as in 0.91.14, `exactory post-problem` is
  the command that refuses a citation that breaks a rule of the post.
- The capacity guard names 51 cells of its property table as gaps (no test drives that property for that form),
  and nine entries of earlier releases keep their gap statement.

## Effects and limits

- A reviewer call can now end with `review_context_unverified` or `review_context_contaminated` before it sends a
  request. Take the step that the details name, then run `review-series` again. On copies of the 24 live stores
  with review assignments, the rule stops none of the 255 heads without a recorded result.
- A store whose review assignments belong to a reading chain keeps its indexed history at each read. This cost
  was measured on copies of the eleven live stores with a reading chain. One read takes 0.12 s to 1.27 s more
  and uses 0.5 MB to 53 MB more memory.
- The selection of version 3 reads the member `recorded_revision` of an earlier first assignment before it
  checks the history of that assignment. The commands write that member with the revision of their commit. Each
  of the 32 first assignments of the live stores holds the right value. An independent review found one
  defect: a value that a direct storage write changed to a later revision removes a ready reading from the
  selection. No changed text gets credit in that case. The next release effort repairs this defect.
- A store keeps its indexed history when a review assignment holds the member `reading_chain`. Release 0.91.14
  kept it when a review assignment held a carried selection of version 2. `review-assignment` writes both
  members together, so a store that the commands wrote keeps its history. A store with the selection and
  without `reading_chain` does not.
- The start of a reviewer call reads the reviewer runtime one more time than before.
- The check of the context refuses one of the 1,628 recorded starts of those stores. That call belongs to a
  superseded assignment. The completed probes of its route record hold another runtime than the route record pins.
- An independent review of the context check found the defects below. The next release effort repairs them.
  - A staged review: a contamination event on a planned child before its first dispatch gives a refusal. The
    member `details.next` of that refusal names the same dispatch. Release 0.91.14 refuses that dispatch without
    the member.
  - A v7 or a math chain: a contamination event on a refused turn changes the plan to a new export. Release
    0.91.14 planned the replacement of that turn.
  - A chain under `exactory-openness-reading-v5` with a size failure and a failed probe of its route record: the
    plan is the probe of that route record. Release 0.91.14 gave the decision with the answer `Run the review on
    another route`. That answer is still correct for a larger verified route.
  - A probe that fails between the plan and the start of a call: `review-series` prints a `record-check` step.
    Run `review-series` again. The new plan names the probe.
  - The handoff `review_context_contaminated` names a context repair that `review-assignment` refuses in two
    cases. The first case is a contamination that only a probe found. A probe that verifies the route record
    ends that state. The second case is the head of an adjudicator without parts.
  - An output correction on another route record than its stale assignment starts without a check of the earlier
    turns, as in 0.91.14.

## Compatibility

- No stored record changes. A stored carried selection of version 1 or 2 verifies under its own rule.
- No transport file changes, so no route record becomes stale because of this release.
- A chain in progress keeps the form that it recorded.

  part and the modules that read every source file.
- On each merged tree: the packet inventory reports no diagnostic, the 214 certificates have no difference, and
  the call rows have no difference. `codex/generate.py --check` and `git diff --check` pass.
- The CI runs the full suite on Python 3.9, 3.12 and 3.14, with eight shards for each version. The run of the
  tree `7ba0e900` ended with success. The run of the tree `91ab3dfc` failed two tests of
  `tests.test_review_runtime_retry`, and this release repairs both tests. The run of the tree of pull request
  #164 was in progress when this note was written.
- Two independent reviews read the diffs of the context check and of the carried selection of version 3. The
  first review found one defect that ends a plan with an error. This release repairs that defect: the plan of
  a capacity replacement on a stale route record keeps its handoff `review_route_runtime_stale`. "Effects and
  limits" lists the other findings.
- The release was merged while the CI run of its last tree was in progress. If a test fails in that run, a
  separate change repairs that test.
