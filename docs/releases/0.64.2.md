# Exactory 0.64.2

This release lets a review read more full text than one route input can
hold. The reviewer keeps verbatim excerpts, and the harness checks each
excerpt against the stored source text. A problem openness review whose
full texts do not fit one input reads them in a chain of turns. The code
came in pull request #57 (`b1c8b51`); this release gives it a version.
The work is recorded in
`misc/harness-improvement/20261027085554-bar-source-requests-exceed-route-capacity`
of the exactory repository.

## Why

Two reviews in one live problem record could not finish. A blind bar
session requested seven full texts, 1,331,003 characters together. Each
continuation delivered some of them, the route fitting left out the
earlier bodies, and the reviewer requested them again for ten rounds. An
openness review carried eight full readings, 1,598,318 characters. The
route withheld five bodies by text priority, and the reviewer did not
accept reading records instead of complete reading. Both totals are above
the route limits (Codex 1,048,576 characters, Claude 1,300,000).

## Reviewer excerpts

- `research_harness/review_excerpts.py` checks each excerpt that a
  reviewer keeps against the stored source text, after NFKC and
  white-space normalization. The first occurrence is delivered, with its
  exact original span, its locator and its SHA-256. An excerpt that does
  not match keeps the reviewer's text, marked as not checked.
- A session has an allowance of 200,000 excerpt characters and 100,000
  passage characters. Excerpts count first-fit, in output order. An
  excerpt or a passage over the allowance is not cut short; it has the
  status `over_allowance`.
- New continuations and context repairs of bar, slate and result sessions
  carry the excerpt rules in their prompt, under the same template id.
  Their packets carry `reviewer_excerpts`: the checked excerpts of the
  session with the allowances used.
- A full-text request for a text that a turn under these rules delivered
  complete is answered with `already_delivered`. A bounded `passage`
  request is answered at once. Neither stays pending. A context repair
  starts a new session, so each text can be delivered once more after a
  repair.

## Openness reading chains

- A `native_math` assignment with a problem openness packet that one input
  cannot hold becomes reading turn 1. Reading turns deliver groups of full
  texts: each turn packs the longest prefix of the remaining texts that
  fits, in text-priority order, as a fresh input without replayed history.
  The packet's reading record carries the continuity.
- The final turn is the native packet with the reading record. It repeats
  a full text only when its input has room, so the reviewer cannot count
  on seeing a text again. A final turn can ask for passages; a final
  reading answer is refused once the passage allowance is used up, so a
  chain always ends.
- The reading and final turns use their own prompts
  (`exactory-openness-reading-v1`) and an output contract for reading
  answers. `problem-openness` records `reading_turns` for a final turn,
  and the openness assessment checks them again. A chain that missed a
  text is refused. A single text larger than one input fails the reading
  turn with `review_input_too_large`.

## Compatibility

- The eleven fingerprinted review modules are unchanged, so registered
  routes stay valid.
- Earlier assignments keep their prompts and stay authenticated. Recorded
  bars, slates and result reviews get no new refresh, calibration or
  regrade obligation.
- A packet that fits one input stays a single turn. Math-solver result
  reviews with an openness minimum keep their behavior.

## Choices for the owner

The owner merged pull request #57 with these choices: excerpts count
first-fit in output order; `too_long` is measured on the matched original
span; bar, slate and result sessions keep their template ids, while
reading chains have their own; a context repair starts a new session for
`already_delivered`; a reading chain packs the longest prefix that fits,
in text-priority order; and a final reading answer is refused once the
passage allowance is used up.

## Not in this release

- Refusing an oversized Codex request before dispatch, instead of
  recording a JSON decoding error. It needs a change of the fingerprinted
  `review_codex_transport.py`.
- Delivering one text that is larger than one input.
