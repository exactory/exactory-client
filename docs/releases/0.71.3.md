# Exactory 0.71.3

This patch makes a store reader treat a rollback journal that a committing writer has just unlinked as absent. In
0.71.1 the reader checked such a journal again, at most three times, and then stopped with `store_busy`.

## Why

0.71.1 fixed `unsafe_path` for a reader whose `stat` of the rollback journal returned the inode that a committing
writer had just unlinked (link count 0). Its bounded recheck could still fail: when another process commits in a tight
loop, the reader can see an unlinked journal three times in a row. CI of main at 6204e75 met this in
`test_review_staged_repair_upgrade`:

```text
store_busy: Research journal changed during access; retry after the writer finishes
```

## What changed

`storage.Store._check_files` treats a `-journal` whose `stat`, or whose `fstat` after opening, reports a link count of
0 as absent, exactly like a journal that does not exist. An inode with no link is reachable by no name, so it cannot be
an alias of a store file. There is no retry and no `store_busy` for it.

Every other check stays: the database file and its publication window, the one-link check of an existing journal and
of its opened file, and the symlink and regular-file checks. `_connection` runs these checks again after it opens the
database, so a journal that a hard link, a symlink or a directory replaces is still rejected with `unsafe_path`.

## Upgrade

No action is necessary.

## Checks

`test_research_storage` (the deterministic race tests of 0.71.1, with the bound test now expecting the read to
succeed), `test_review_staged_repair_upgrade`, `test_review_task_execution_worker` and `test_review_task_execution`
pass on Python 3.12.8 and 3.9.6, and without `PYTHONPATH` as CI runs them, with the manifest and version tests at
0.71.3, `codex/generate.py --check` and `git diff --check`.
