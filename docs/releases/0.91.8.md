# Exactory 0.91.8

This release applies the rules of a problem post to the texts of a record when the record takes them. A text that
the post refuses is thus refused before the reviews. The release also examines the shape of every entry of the
accounts before it reads the entry, so that a `problem-value` payload with a wrong shape gets a refusal with a
code. The release follows 0.91.7. Its record is
`misc/harness-improvement/20261119212253-impact-of-a-resolution-lineage-and-future` of the exactory repository.

## What changed

The texts of a post:

- `exactory post-problem` sends seven texts from the record: the title, the statement, the details of the
  statement, the resolution criteria, the motivation, the section "What a resolution would change" and the current
  state. The server has a length rule and a character rule for each. Before this release the record had the length
  rule for one of these texts only.
- `problem-statement` now applies the rules to the title, the statement before the `---` line, the details after
  it and the resolution criteria. A text that breaks a rule is refused with `problem_statement_post_text_invalid`.
  The details name the `field` and the `rule` (`length`, `character` or `separator`).
- `problem-value` now applies the rules to the joined text of each of its three sections. A text that breaks a
  rule is refused with `problem_value_post_text_invalid`. The details name the `section` and the `rule` (`length`
  or `character`).
- The rules have one definition, in `research_harness/exactory_api.py`. `exactory post-problem` reads the same
  definition, and its messages are those of the release before this one.

The shape of a payload:

- `problem-value` examines the members of every entry of the accounts before it builds the list of the entries
  and before it follows a reference. Before this release, an entry with a member of another entry kind ended with
  a Python exception.
- A test changes every member of a valid `problem-value` payload and of a valid `problem-statement` payload, one
  at a time. It also gives an entry the members of another part. Each of the 7,684 changed payloads gets an
  acceptance or a refusal with a code. Before this release, 57 of them ended with a Python exception.

The commands `exactory` and `exactory-cohort` held code that no caller used: a second copy of the UTF-16 count, a
function that cut a text to a count of UTF-16 code units, and four limits. This release removes that code. The
UTF-16 count has one definition, in `exactory_api.py`.

Incident ledger: 2 entries set to 0.91.8.

## Compatibility

No transport file and no reviewer prompt differs from the release before this one, so no reviewer route becomes
stale. Stored records keep their bytes and their digests. The new rules apply only when a new statement or a new
value record is written.

The code `problem_changes_if_resolved_length` of 0.91.6 no longer occurs. `problem_value_post_text_invalid` with
`section: changes_if_resolved` and `rule: length` takes its place.

Three kinds of payload that the release before this one accepted are now refused:

- A `problem-value` payload whose motivation or current state has fewer than 100 or more than 10,000 characters.
  Make the text longer or shorter.
- A `problem-statement` payload whose title, statement, details or resolution criteria are outside the lengths of
  the post, or whose statement has more than one `---` line. The message gives the limits.
- A payload of one of the two commands with a control character other than a tab or a line break in one of these
  texts. Remove the character.

A payload with two defects can get another refusal than before, because `problem-value` now examines the members
of the accounts first. A payload with one defect in the members of an entry can also get another code. An
alternative without `role` or `neighbour` got `problem_neighbour_role_missing`, and it now gets `invalid_input`. A
`strength` entry that is no object, or that has no `id`, got `invalid_input`, and it now gets
`problem_strength_incomplete`.
