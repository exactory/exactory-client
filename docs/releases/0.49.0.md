# Exactory 0.49.0

This release repairs the launcher, the math-solver launch, the experiment
guard, assessment and arXiv identifiers. A study, the test runs and the
independent reviews of September 2026 found these problems (harness record v11,
tasks H4, H10, H11, H12 and H14, and Problem 12). The other v11 tasks (H2, H3,
H6, H13 and H15) come in a later release.

## A worker that starts slowly keeps its run

Before this release, `exactory-lab run` waited 5 seconds for the local worker
to report that it was ready. On a loaded machine the worker often needed more
time, and the launch ended with `execution_recovery_required` although the
worker was alive.

- For a local run, the launch now waits for a live worker to become ready for
  up to the binding's `timeout_seconds` plus 10 seconds. A worker that exits
  before it is ready, or that is not ready in that time, still ends the launch
  with `execution_recovery_required`, and the program does not run. Record that
  run with `reconcile-run`, giving `resolution: "interrupted"` and a reason.
- After the worker receives its token, the launch waits up to `timeout_seconds`
  plus 10 seconds for the run to end, and then up to 6 more seconds for the
  worker to exit: at most `timeout_seconds` plus 16 seconds. A worker that ends
  in that time gives the run's outcome. A worker that is still live ends the
  launch with `execution_recovery_required`, and `reconcile-run` records the
  outcome after the worker ends.
- Three cases ended the launch with a Python traceback and left the claimed run
  without an outcome. Now:
  - a worker that ends in the 6 seconds after the wait for its run gives the
    run's outcome;
  - a worker that ends before it reads its token ends the launch with
    `execution_recovery_required`;
  - a worker process that cannot start (for example at the process or
    open-file limit) ends the launch with `execution_recovery_required`.

  In the last two cases, record the run with `reconcile-run`, giving
  `resolution: "interrupted"` and a reason.
- A run timeout longer than about 24.86 days launches as in 0.48.0.

## The math-solver launch no longer ends with a traceback

The math-solver search controller had the same fixed 5-second wait. It now
waits for a live launcher to become ready for up to `timeout_seconds` plus 10
seconds, the bound of its wait for the run.

Five cases ended a launch with a Python traceback. Now:

- A refused launch waits once, 5 seconds, for its launcher to end, and then
  raises the refusal. When the launcher had not received its token and ended in
  that time, its run is reconciled first. A launcher that is still live ends
  the launch with a `SearchError` of code `recovery_required`, and its details
  name the refusal (`refusal` with its `code`, `message` and `details`). In
  0.48.0 a launcher that ended during the second of two such waits gave a
  traceback.
- A run that outlasts the wait for it, and whose launcher ends within the
  5-second exit wait, is reconciled, and the launch returns its outcome. A
  launcher that is still live ends the launch with `recovery_required`.
- When a launcher ends before it reads its token, the launch returns, and
  reconciliation records the run as indeterminate with its reserved units
  charged.
- A launcher process that cannot start, and a failed write of the run
  directory (for example on a full disk), end the launch with
  `recovery_required`. The details name each error by its step (`start_error`,
  `record_error`, `reconcile_error`). The launch records the run as never
  started, and no unit is charged. When that record cannot be written, the run
  stays reserved: `search reconcile` records it as never started if the record
  exists, and otherwise as indeterminate with its reserved units charged. When
  the record was written but the reconciliation failed, the run stays reserved
  until `search reconcile` records it as never started.

## The experiment guard reads the target of a write

Before this release, the experiment guard denied every command in which `>`,
`>>` or `tee` came before a later `.exactory/` path, and it read heredoc bodies
as commands. So it refused reads of workspace state such as
`cat .exactory/authorship.json 2>/dev/null && python3 -m json.tool .exactory/study.json`.

- The guard now denies a write of workspace state only when the target of an
  output redirection, or a file argument of `tee`, is a path under
  `.exactory/`. It reads the target without its quotes and escapes. The
  redirections are the bash and zsh output forms: `>`, `>>`, `>|`, `>&`, `&>`,
  `&>>`, `<>`, and the zsh forms with `!`, such as `>!` and `>>!`.
- A heredoc body that nothing runs is data, so a note that quotes a denied
  command is accepted. A body stays checked when the command line can run its
  text, for example through a shell, `eval`, `source` or the dot command. A
  body also stays checked when the guard cannot read the heredoc as the shell
  does.
- Every other rule keeps its pattern and its reason.

## Assessment refuses a passed validity check without validation evidence

- `assess` refuses a validity check marked `passed` whose evidence holds no
  completed output of a planned `validation` requirement. The error code is
  `validity_evidence_missing`, and `details.check_ids` names every such check.
  Cite the completed validation output, or record the check as `unresolved`.
- The refusal comes before any write. The store revision stays the same, so
  the same request ID can carry the corrected payload.
- Stored assessments evaluate as before. A payload that is recorded again, for
  example an `inheritance_refresh` reassessment after an objective change, is
  checked as a new assessment.

## Old arXiv identifiers that lost their hyphen

- An old-style arXiv identifier whose archive name lost its hyphen now
  normalizes to the hyphenated archive: `arxiv:astroph/0410063` becomes
  `arxiv:astro-ph/0410063`. The map holds the 30 hyphenated archives of the
  old identifier scheme.
- A bundle whose bibliography target is not in canonical form is still
  refused. The error details now give the target and its canonical form.
- In an existing store, a reference target without the hyphen now resolves to
  the hyphenated work when that work is acquired. An `acquire` or `expand` that
  reuses the request ID of an earlier call without the hyphen fails with
  `request_id_conflict`. Give it a new request ID.

## A partial computational result and the direct publication paths

- The workflow document states why a partial result does not pass readiness.
  It gives the route after the user authorizes a narrower objective (0.47.0):
  a successor cycle under the new objective that inherits the checkpoint's
  validated result.
- Without that authorization, the study can publish only on the direct paths.
  Park a study that finished there with `exactory-lab state set --waiting
  <reason>`. The autopilot Stop hook now says so.

## The math-solver attack guard

The README and the hook's own text now state what `hooks/guard_attack_files.py`
checks. It denies a Write or an Edit to a file that the harness writes. It
also denies a shell command that writes (a word that begins with `>`, or `tee`,
`cp`, `mv`, `rm`, `truncate`, `dd`, or `sed -i`) when one of its words names
such a file by a path that contains a `/`. In a managed search tree, the
managed guard denies these writes first.

## Known limitations

- The attack guard reads the words of a command, not its write targets. In an
  attack workspace outside a managed search tree, it misses a write to a
  harness file by its bare name (`echo x > journal.jsonl`), a write after a
  `cd` in the same command, a redirection whose word does not begin with `>`
  (such as `2>`, `&>` or `x>file`), `>|file` without a space, and `dd of=`.
  It also denies a writing command that only reads a harness file, such as
  `cp attack/foo/journal.jsonl /tmp/copy.jsonl`. A later release reads the
  targets (task H15).
- Python 3.9.6 accepts a command payload with an integer of more than 4300
  digits, which Python 3.11 and later refuse to read back from the store. A
  record value nested several hundred levels deep (600 in a probe) is stored,
  but the guarded snapshot of the store then fails with `RecursionError`. A
  later release bounds every stored value (task H13).
- The literature repairs of v11 (tasks H2, H3 and H6) are not in this release.
- In the math-solver launch, a run directory that already exists still ends the
  launch with `FileExistsError`, and an `OSError` from `reconcile_runs` still
  ends it with a traceback. `SEARCH.md` does not yet say that the launch writes
  the never-started record itself when no launcher started. `search reconcile`
  judges a launcher live only by its lock file, so a reconcile while a launcher
  is still starting records its run as indeterminate.
- Tests with short run timeouts or fixed time windows can fail on a heavily
  loaded machine, on this release and on 0.48.0 alike. In the verification
  runs of this release, such a failure passed on rerun, or failed the same way
  on 0.48.0.
