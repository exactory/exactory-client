# Exactory 0.48.0

This release repairs the local launcher and its run records. A study met these
problems in September 2026 (harness record v11, tasks H1, H7, H8 and H9; the
same image-output problem is task N5 of v12). The other v11 tasks (H2, H3, H4,
H6, H10, H11 and H12) come in a later release.

## A venv interpreter keeps its packages

Before this release, `bind-run` recorded the resolved interpreter file of the
admitted `argv[0]`, and the worker started that file. The `bin/python3` of an
ordinary venv (made with `python3 -m venv`) is a symbolic link to the base
interpreter. The program therefore ran on the base Python without the venv's
packages.

- When the admitted `argv[0]` is a symbolic link, the binding's `runtime` is
  `{path, resolved_path, sha256, python}`. `path` is `argv[0]` as admitted,
  `resolved_path` is the file behind the link, and `sha256` is the SHA-256 of that
  file. The worker starts the link, so the program imports the venv's packages.
- A regular interpreter file keeps the record of earlier releases: `path` is its
  resolved path, and the record has no `resolved_path`.
- The launcher compares the whole record when it claims the run. Changed
  interpreter bytes, a changed Python version, or a link that now resolves to
  another file stop the launch with `execution_runtime_changed`, and nothing is
  claimed. If the interpreter changes after the claim, the worker refuses to
  start the program, and the launch returns `execution_recovery_required`.
  Record that run with `reconcile-run`, giving `resolution: "interrupted"` and a
  reason.
- A binding that exactory-client 0.47.0 or earlier recorded for a link keeps the
  resolved file as its `path`. Its launch starts that file, without the venv's
  packages. `bind-run` with the same payload returns that binding. To run the
  program with the venv's packages, admit and bind a new run.
- The shared-folder runner (`exactory-lab colab-serve`) started with a venv link
  starts each program with that link and records the file behind it as
  `resolved_path`.

## How to start bind-run and the launch for a venv

`bind-run` and `exactory-lab run` still check the admitted interpreter against
the Python that runs them: the admitted `argv[0]` must resolve to the same file,
and the admitted Python version must equal that Python's version. Both commands
start with the `python3` found on `PATH`. For an admission whose `argv[0]` is a
venv interpreter, start them with that interpreter, where `VENV` is the venv
directory:

```sh
VENV/bin/python3 "$(command -v exactory-research)" bind-run --file run-binding.json --expected-revision REVISION --request-id bind-cycle-001
VENV/bin/python3 "$(command -v exactory-lab)" run code/program.py --admission run-001 --backend local --timeout 30 --expected-revision REVISION --request-id launch-cycle-001
```

The workflow document, the CLI reference and the experiment skill show the same
commands.

## Result and validation evidence need text or JSON outputs

An assessment cites `result` and `validation` evidence through a locator into
the output's text or JSON. Before this release, a plan could bind a figure or a
PDF to a `result` requirement, and no locator could cite it, so the assessment
never had a validated result.

- `bind-run` refuses, with `invalid_execution`, an output bound to a `result` or
  `validation` requirement unless its media type is `text/*`, `application/json`
  or a `+json` type. Bind figures and other binary files to a `log` requirement,
  and draw figures from a JSON result.
- The rule also refuses `application/xml`, `application/yaml` and
  `application/x-ndjson` for these two kinds. Declare such outputs as `text/*` or
  bind them to a `log` requirement.
- The rule applies to a new binding only. `bind-run` with the payload of a binding
  that an earlier release recorded returns that binding.

## The run metric can come from the declared validation output

Before this release, the metric came only from a stdout line with a `metric` key
or from `results/SCRIPT_STEM.json`. A program that wrote its summary under
another name reported `ok: false` and no metric although it completed.

- The metric now comes from the first of three sources that gives one: the last
  stdout line with a `metric` key, the fallback file `results/SCRIPT_STEM.json`,
  and the first declared `application/json` or `+json` output of a `validation`
  requirement. The run configuration records the third source as
  `metric_output`.
- For a run that this release claims, a source gives a metric only when its JSON
  is finite, nests at most 32 levels, and holds no integer of more than 4300
  digits. Python 3.11 and later refuse to read a longer integer, so this keeps
  every recorded metric readable by every supported Python. A metric that fails
  the bound gives no metric, and the run reports `ok: false`.
- A run that 0.47.0 or earlier claimed keeps the rules of its release, so its
  recorded metric stays valid.
- As with the fallback file, the whole metric JSON is copied into the run's
  records and receipts. Keep a validation output that serves as the metric small.

## Known limitations

- Four timing tests that predate this release failed on a heavily loaded machine
  (load average 28 to 58), on this release and on 0.47.0 alike. They passed at a
  load average of 4 to 16.
- Python 3.9.6 accepts a command payload with an integer of more than 4300
  digits, which Python 3.11 and later refuse to read back from the store. The
  metric bound above covers run metrics only. The general case is recorded for a
  later release.
