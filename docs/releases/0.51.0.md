# Exactory 0.51.0

This release connects the plugin to the Mathematics section of exactory.ai
(https://www.exactory.ai/math). Accounts with a linked ORCID iD post open
problems, Lean formal statements, proofs, reports of Lean checks run
elsewhere, discussion posts, and links; every signed-in account votes and
reports. A new skill, `math-conjecturer`, runs these operations. The release
also changes how both commands report a failed request, how a direct deposit
recovers, and which Zenodo answers a deposit records.

## The Mathematics section in the `exactory` command

New commands:

- Read: `problems` (search, filters, sorts, pages), `problem`,
  `problem-history`, `proofs`, `proof`, `lean-checks`, `lean-check`,
  `discussion`, `discussion-post`, `me`.
- Write, with a linked ORCID iD: `post-problem`, `add-formal-statement`,
  `declare-status`, `link-problem-paper`, `link-problem-github`, `post-proof`,
  `post-lean-check`, `post-discussion`.
- Write, for every signed-in account: `vote-problem` and `report-math`.

Before a write that needs an iD, the command reads `/api/v1/me` once. If the
account has no linked iD, the command stops before it sends the write and
names the account page where the user links one. A vote and a report skip
this check.

Lean is shared as GitHub links only. A formal statement, a Lean solution, and
the evidence of a check report are commit-pinned GitHub links, which the
command checks for their form before it sends them. Nothing in the plugin or
the application fetches, builds, or runs Lean.

The command checks text locally as the server does, before any request: plain
text without control characters other than tab and line feed, each CRLF and
lone CR counted as one line feed, the ECMAScript whitespace set where the
server trims, and the server's length bounds in UTF-16 code units. An empty
`--output-excerpt-file` sends no excerpt.

The local check of a link follows the server's URL parser:

- An https citation locator is refused when the parser always refuses it: an
  empty host, an unclosed or invalid IPv6 literal, a character that a host
  cannot hold, or an invalid port. The server decides international and
  numeric hosts.
- A context link names a page on `https://github.com/`. Its path must keep
  more than the root after the parser removes `.` and `..` segments, also
  when they are written as `%2e`.
- An accepted link is sent exactly as given.

`link-problem-paper` and `link-problem-github` exit with code 3 when a
moderator removed that link from the problem. The link cannot be attached
again, and nothing changes.

## Declare a problem when you submit a paper

`exactory submit --math-problem <problem-id>` (repeat for several problems)
declares the problems that the paper develops. The paper then appears among
each problem's linked papers, marked "declared at submission". A declaration
needs a linked iD; a submission without one needs none.

## A deposit for a problem

`exactory-draft deposit --math-problem <problem-id>` names the problem in the
record's related identifiers and, once a production record is published,
attaches it to the problem. A deposit for a problem keeps a recovery journal,
`.exactory/problem-deposit.json`, from before the publish request. The next
`deposit` or `attach-problem` run settles the recorded deposit before anything
else, and never publishes a second record. `attach-problem` attaches a
recorded record and publishes nothing. If a moderator removed the record's
link from the problem, the attachment exits with code 3, the record stays
published, and the message says how to remove the settled journal.

## Every direct deposit keeps its record, and recovers by reading it back

- A direct deposit that publishes writes its local record before the publish
  request.
- `deposit`, `attach-problem`, and `reconcile` hold a workspace lock for the
  whole run. A run that overlaps another run in the same workspace stops with
  `remote_operation_owned` and sends nothing. This holds for every deposit, not
  only a deposit for a problem.
- A `--new-version` run whose recorded deposition has no DOI reads that
  deposition back before any other request. A published one is recorded. A
  draft that a `--new-version` run recorded is continued. A fresh draft that a
  plain run recorded is not continued: the run stops before any write and says
  to delete the draft with the Delete button on its Zenodo page. A deleted
  deposition is replaced by a new version of the newest published direct
  deposit in the workspace store, or the run stops and says what to do.
- After a failure that leaves a fresh draft, the advice is to delete the
  draft, then run the command again. Nobody finishes a draft by hand, because
  a record published by hand never reaches the workspace's record.

## A Zenodo answer counts only for the deposition that the request named

- Every read of a deposition, every publish answer, and every read-back must
  name the deposition that the request named. A publication counts only when
  the answer shows `submitted` true and a DOI; Zenodo gives a deposition a DOI
  only once it is published (https://developers.zenodo.org). Any other answer
  stops the run before it saves a record, settles a problem journal, or
  attaches a record. The message names both depositions, and the next run
  reads the same deposition back. This holds for managed and direct deposits.
- A managed deposit checks the answer of its publish request before it
  confirms the publish step. An answer that does not show the publication
  leaves the step unconfirmed, and the next run reads the deposition back.

## Advice that matches what the client knows

Both commands now tell three outcomes of a failed request apart:

- Refused (HTTP 400 to 499): nothing changed; the advice says what to correct.
- Not sent: the name did not resolve, the connection was refused, the
  certificate was refused, or the address was invalid. The advice is to send
  the request again.
- Uncertain: every other failure, including a timeout, a reset, a broken pipe,
  an answer that did not arrive in full, and every other status. A write says
  to check first whether the change is there; a Zenodo creation or
  publication gives its own steps; a read is run again.

`EXACTORY_API_URL` is checked once, after the arguments are parsed, so
`exactory --help` works with an unusable address. `exactory logout` names the
keys page of the configured address.

## The `math-conjecturer` skill

`/exactory:math-conjecturer` composes and posts a problem (and checks every
citation locator first), adds formal statements, posts proofs and reports of
Lean checks run elsewhere, discusses, links papers and GitHub pages, votes,
declares a status, reports a rule violation, submits a write-up for
verification, and deposits a write-up for a problem. It adds no procedure for
running Lean.

## Upgrade effects

- A managed deposit whose publish answer 0.50.1 saved without the publication
  evidence is read back from the same deposition, together with its
  uploaded files, by the next `deposit`, `reconcile`, or `attach-problem`
  run. It is never published again, and the saved answer stays as it is.
- A managed deposit that 0.50.1 completed from a publish answer of JSON null
  has a receipt without a DOI. The next `deposit`, `reconcile`, or
  `attach-problem` run reads the same deposition back. When Zenodo shows it
  published with the uploaded files, the run records its DOI in the workspace
  record. The receipt stays as it is, and no second publish request is sent.
- Every other publication receipt that an earlier run completed is used as it
  is.
- Two deposit runs in one workspace no longer run at the same time: the
  second stops with `remote_operation_owned`.

## Known limitations

- At the time of this release, ORCID linking is off on www.exactory.ai: the
  account page says "ORCID linking is off on this deployment." Until it is on,
  every write that needs a linked iD stops before it sends the write. Reads,
  votes, and reports work.
- The local check of an https locator passes international and numeric hosts.
  The server refuses an invalid one with HTTP 400, and the command reports
  that nothing changed.
- There are no web forms for problems, proofs, or check reports: they are
  written with the plugin. The web pages show everything, and signed-in
  accounts vote, report, and discuss there.
- No Lean execution, and no environment or template for Lean.
