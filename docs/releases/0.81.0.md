# Exactory 0.81.0

This release gives every stop of the research harness a class, and lets the harness pass one kind of stop by
itself: a stop that the harness records as its own defect. It follows 0.80.0. It is phase C of the work recorded in
`misc/harness-improvement/20261106085323-override-of-harness-stops` of the exactory repository.

## Why

The owner accepted this principle on 2026-11-06. With the user's instruction, any gate can be passed, and the fact
is recorded. Without an instruction, a stop passes only when the harness itself classifies it as its own defect. The
agent's own judgment is never the trigger. 0.79.0 and 0.80.0 built the first half. Until this release, a run that a
harness defect stopped waited for the user like every other run.

## What changed

- Every stop code has one class: `waiting`, `harness_defect` or `decision`. One function, `classify_stop` in
  `research_harness/stop_classes.py`, derives it from the code. The waiting list is `store_busy`, `rate_limited`,
  `review_provider_unavailable`, `review_capacity_wait`, `review_invocation_pending`, `provider_state_capacity` and
  `lock_timeout`. The harness-defect list has one code, `review_series_no_progress`: the planner asked the driver to
  run an action that had already run successfully, at the same recorded progress. Every other code, a new one
  included, is a decision stop. No input of the agent changes the class.
- `review-series` prints `stop_class` on its `stop` and `wait` lines. When it ends in a stop, it records the stop in
  the store as `review_series_stop` and prints its `stop_id`, or `stop_record_error` when the record could not be
  written. The error output of `exactory-math search` also carries `stop_class`.
- New command `exactory-research gate-auto-pass`. Its payload holds only the `stop_id` of a recorded
  harness-defect stop. The command checks the stop record and the current state of the study, and then moves the
  study from `experiment` to `write`. It keeps every unmet gate item listed, creates no review, score, acceptance
  or decision, and writes a local report under `.exactory/automatic-passes/`. Budgets and an explicit quality
  condition of the user stay binding. A second automatic pass of the same gate needs the user's instruction. With
  `--check`, the command checks and records nothing.
- After an automatic pass, every public write from the workspace needs the user's recorded instruction: a
  submission, a verdict, a problem post, a deposit, and every other write of `exactory` and `exactory-draft`.
  Without it, the command refuses with `gate_override_public_write` before the write. `gate-override` accepts an
  optional `public_action`, the exact `METHOD /path` of one write.
- `status`, `next`, `final/`, the deposit archive and the deposit description show an automatic pass.
- `docs/research-workflow.md` ("Stops and overrides"), `docs/research-cli.md` and the skills describe the classes,
  the automatic pass and the public-write rule.

## What stays the same

- A workspace without `.exactory/automatic-passes/` sends its public writes as before. The check does not open the
  store in that case.
- A stop that is not a harness defect passes only on the user's instruction, as in 0.79.0 and 0.80.0.
- Records written by earlier releases do not change, and no migration is necessary. A survey of the 21 live records
  found no stop that qualifies for an automatic pass.

## Known limits

The Astra 6 reviews of this change found problems that the next release fixes:

- The managed path of `submit`, `verify` and `deposit` checks the gate name only. Record the user's instruction for
  these writes with its gate (`submitted`, `verification`, `publication`), not with `public_action` alone.
- The second-pass limit compares gate names, so `readiness` and then `manuscript-readiness` can pass the same move
  twice.
- A workspace that holds only `.exactory/automatic-passes/`, with no store and no draft files, is not checked.
- A result packet that is not JSON turns the final stop of `review-series` into `exit 1` with `input_io`.
- The deposit description of an automatic pass is a machine-style line.
- The command recognizes a move from `evaluate` to `deposit`, but a managed study cannot meet both its conditions.
- Several sentences of the texts need corrections.

Whether a plugin older than 0.81.0 reads a store that holds the new records was not checked.
