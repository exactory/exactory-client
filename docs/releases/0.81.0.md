# Exactory 0.81.0

This release gives every stop a class that the harness derives from its code, and lets the harness pass one class
of stop on its own: a stop that it classifies as its own defect, within recorded bounds. It follows 0.80.0. It is
phase C of the work recorded in `misc/harness-improvement/20261106085323-override-of-harness-stops` of the exactory
repository. GPT 6 Astra at effort `xhigh` reviewed the design, and the owner authorized the implementation on
2026-11-06; the owner's instruction of 2026-11-07 started phase C before phase B had run on real records.

## Why

- The owner accepted this principle on 2026-11-06: with the user's instruction, any gate of a pipeline can be
  passed, and the fact is recorded; without an instruction, a stop can be passed only when the harness itself
  classifies it as its own defect, and the agent's judgment is never the trigger. 0.79.0 and 0.80.0 built the first
  half. Until this release the second half had no mechanism: the texts said that a stop the harness itself causes
  passes by no rule of its own, so a run stopped by a harness defect waited for the user like every other run.
- `review-series` stops with `review_series_no_progress` when the planner asks it to execute the same action at the
  same recorded progress a second time. Only the harness can cause that: the driver dispatched the action through
  its own operation table, the dispatch succeeded, and the planner chose it again. Before this release the driver
  printed that stop and kept no record of it, so nothing durable could ground a pass. The survey of the 21 live
  records found 0 stopped-series rows and 0 failed-hook rows in the stores: stops left no durable trace.
- The same survey found 95 failed review runs, 16 output refusals and 5 failed route probes, none of which qualifies
  as a harness-only cause: 73 `review_transport_failure` rows mix usage limits, API errors, malformed answers and
  empty turns; the size, format and quality codes depend on material the author controls; `review_failure_unknown`
  is unknown. A code with a mixed or unknown cause stays a decision stop.

## What changed

- Every stop has a class, `waiting`, `harness_defect` or `decision`, derived from its code by one function,
  `classify_stop` in `research_harness/stop_classes.py`. The waiting list is `store_busy`, `rate_limited`,
  `review_provider_unavailable`, `review_capacity_wait`, `review_invocation_pending`, `provider_state_capacity` and
  `lock_timeout`. The harness-defect list is `review_series_no_progress`. Every other code, a new one included, is a
  decision. A test keeps the two lists disjoint and checks that every entry is a code that the plugin raises or
  emits. No input of the agent changes the class.
- `review-series` prints `stop_class` on every `stop` and `wait` line that has a `code`. When a run ends in a `stop`
  with a `code` and a `head_id`, the driver writes the record `review_series_stop/<id>` before it prints the last
  line: `origin: "harness"`, the code, the head's `assignment_id`, the whole plan, a `retry` entry (for
  `review_series_no_progress` the policy `one_execution_per_progress_position` with `executions: 1`,
  `exhausted: true`, the `action_state`, the `action_digest`, the `progress_digest` and the `successful_request_id`
  of the first execution; `terminal_plan` for every other code), the request id, the recorded revision and the
  `scope` that an automatic pass of this stop would have. The last line carries `stop_id`, or `stop_record_error`
  when the record could not be written. An intermediate stop that the driver plans again writes no record. The
  `details` of a `review_series_no_progress` stop add `action_state`, `action_digest`, `progress_digest` and
  `successful_request_id`. There is no command for writing a stop.
- `exactory-research gate-auto-pass --file FILE --expected-revision N --request-id ID`, with `--check`, records the
  automatic pass of one recorded harness-defect stop. The payload is `{"stop_id": ID}` and nothing else; the
  command takes no gate, class, reason, scope or transition from the caller. It checks that the record exists, that
  the driver wrote it and that it is unchanged, with its receipt and the committed successful dispatch; that its
  code is on the harness-defect list; that its retry schedule ended; that it binds one of two moves, `experiment`
  to `write` through `readiness` (or `manuscript-readiness` under a source-limited contract) for a stopped `result`
  review, and `evaluate` to `deposit` through `publication` for a stopped `manuscript` review; that no automatic
  pass of that gate is recorded; that the stage, the review target and the chain's next action are still those of
  the stop; that the review allowance, the resource obligations, the strategy accounts and the study's loop budget
  permit further work; that the current intent states no explicit quality condition; that the gate lacks exactly
  the review that the defect prevented, with no rejecting review retained and, for `publication`, the `round` gate
  ready; and that a qualifying stop exists for every missing review, from distinct reviewers. The refusal codes are
  `gate_override_stop_missing`, `gate_override_stop_untrusted`, `gate_override_stop_class`,
  `gate_override_retry_pending`, `gate_override_internal_only`, `gate_override_user_required`,
  `gate_override_stop_stale`, `gate_override_budget_exhausted`, `gate_override_quality_condition`,
  `gate_override_other_obligations`, `gate_override_reviews_uncovered` and `gate_override_report`; the existing
  `gate_override_invalid` refuses any other field.
- A pass appends `gate_override/automatic:<digest>` with `authority: "harness"`, `evidence: "recorded_stop"`,
  `stop_id`, `stop_code`, `cited_stops`, `transition`, `target_digest`, the gate's obligations, `report_path` and
  `report_artifact`, and sets the study to the destination stage with `status: in_progress` and no waiting marker;
  a move into `write` records the draft workspace as `exactory-lab state set` does. Before the commit the command
  writes `.exactory/automatic-passes/<digest>.json` with `recorded: false`; a report that cannot be written stops
  the pass (`gate_override_report`), and a store refusal after it leaves the pending file, which `status` and
  `next` list under `unrecorded_overrides` with `recorded: false` and which grants nothing. After the commit the
  report says `recorded: true` and the views are rendered. The same request replays its receipt and restores the
  report. No gate reads the record, no review, score, acceptance, decision, publication receipt or problem post is
  created, and the stage check ignores the record, so `exactory-lab state set` gains no move from it. A second
  automatic pass of the same gate, also after a return to that stage, is refused with `gate_override_user_required`
  and needs the user's instruction through `gate-override`.
- A problem record and a math-solver objective have no study stage, so no stop of theirs binds a move;
  `gate-auto-pass` refuses them with `gate_override_internal_only`, and the texts say to report a `harness_defect`
  stop there like a decision stop. The error output of `exactory-math search` carries `stop_class`, derived from
  its `code` by the shared function. The controller records no stop and passes none on its own.
- After an automatic pass, every public write from the workspace needs the user's recorded instruction. Once the
  store holds an override with `authority: "harness"`, or `.exactory/automatic-passes/` exists, `exactory` checks
  every request whose method is not GET or HEAD, except `POST /api/v1/email-codes` and `POST /api/v1/api-keys`, and
  `exactory-draft` checks every request to Zenodo whose method is not GET, HEAD or OPTIONS. A write is covered by an
  override with `authority: "user"`, in the store or in `.exactory/unrecorded-overrides.jsonl`, that names its gate
  without `public_action` (`submitted` for `POST /api/v1/verifications`, `verification` for a verdict, `post` for
  `POST /api/v1/math-problems`, `publication` for every Zenodo write) or carries its exact `public_action`.
  Otherwise the command refuses with `gate_override_public_write` before any request is sent, and the details carry
  `gate`, `public_action` and `next`. The managed path of `submit`, `verify` and `deposit` runs the same check with
  the gate only. When the store cannot be read and `.exactory/automatic-passes/` exists, only an entry of the local
  log covers a write. Before any automatic pass, the publication commands run as before.
- `gate-override` accepts the optional `public_action`, the exact `METHOD /path` of one public write of `exactory`
  (`POST`, `PUT`, `PATCH` or `DELETE`, a space, a path that starts with `/`, on one line; `gate_override_invalid`
  otherwise). An override with it covers that one write and none of the gate's writes. The transports read the field
  only after an automatic pass; a record without it keeps its meaning.
- `status` and `next` show an automatic pass under `overrides` with `authority: "harness"`, `stop_id`, `cited_stops`
  and `report_path` in place of the instruction text, and `public_action` when a user override has one; the
  `--summary` views cut `stop_id` at 96 characters. `final/overrides/<id>.json` renders the record. The archive of
  `exactory-draft package` adds `review_series_stop` to its record kinds and holds the report artifact. The deposit
  disclosure of 0.79.0 names the gates of user overrides only; a deposit made while the store holds an automatic
  pass, or while a pending report exists, adds one paragraph per entry: "Automatic continuation entry: gate=<gate>;
  defect=<stop code>; stop=<stop id>; store-confirmed=<true or false>. Review approval is separate."
- `docs/research-workflow.md` has three new subsections under "Stops and overrides": "The class of a stop", "The
  automatic pass" with the checks and a table of the refusal codes and their next action, and "Public writes after
  an automatic pass". The sentence that the harness passes no stop on its own is replaced. `docs/research-cli.md`
  has the `gate-auto-pass` row, `public_action` in the `gate-override` row, and the stop record in "Review chains
  and `review-series`". `docs/research-cli-examples.json` has the `gate-auto-pass` example. The `ai-science`,
  `math-solver`, `verify` and `math-conjecturer` skills read `stop_class` at a stop of `review-series`; the `write`,
  `deposit`, `submit` and `verify` skills state the automatic pass and the public-write rule where they apply;
  `SEARCH.md` states `stop_class` in the controller's error output.
- The regression ledger has one new `real_shape` entry, `override-automatic-harness-defect`, with eight tests, and
  `fixed_in: open`. Its positive fixture is a modeled store shape built from a real finite execution and its real
  review records; it is not a measured production incident, and no live record was advanced.

Records written by earlier releases do not change. `review_series_stop` records and automatic `gate_override` records
exist only after this release writes them. Whether a plugin older than 0.81.0 accepts a store that holds the new
record kind was not checked in this draft. No migration is necessary.
