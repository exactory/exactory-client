# Exactory 0.66.0

This release hardens the Codex reviewer routes and adds a check mode to
the research CLI. The work is recorded in
`misc/harness-improvement/20261026230912-math-solver-repairs-0-64-0`
(`TASKS.md`, section T8) and
`misc/harness-improvement/20261024163824-open-records-v13-v15-v16-v17`
of the exactory repository.

## Codex reviewer routes

These changes come from the records
`20261027070717-codex-code-mode-tool-unverifies-review` (T1, T2) and
`20261027085554-bar-source-requests-exceed-route-capacity` (T3).

- All three Codex transports (text, framed and visual) pass
  `features.code_mode`, `features.code_mode_host`, `features.code_mode_only`,
  `features.js_repl` and `features.js_repl_tools_only` as false. On Codex
  CLI 0.163.0 these settings stop code execution: when a model calls the
  `exec` tool, the call returns "code-mode host is disabled" and runs no
  code. They do not remove `exec` from the model's tool list. A live check
  on `gpt-6.1-sol` found no setting that removes `exec`, `wait`,
  `request_user_input` or the `collaboration` tools, so a reviewer that
  calls one of them still leaves an unverified attempt.
- A tool call in a Codex rollout is recorded as the issue
  `tool_call:<name>` (for example `tool_call:exec`) instead of the generic
  `unknown_or_tool_input`.
- An input above the Codex route limit is refused before dispatch with
  `review_input_too_large`, so no JSON decoding error is recorded for it.
  The visual transport uses the same code instead of `review_input_limit`.
- A failed or timed-out run keeps the last 20 lines of the CLI's standard
  error output, at most 4,096 bytes, in the attempt evidence.
- The Codex transports check the recorded runtime against the runtime
  pinned in the route, as the Claude transport does since 0.64.0.

## Check mode for research mutations (v15)

Every mutating `exactory-research` command accepts `--check`. The command
reads one authenticated snapshot, runs the operation's own validation and
preparation, and reports the first refusal or
`{"check": "accepted", "revision": N}`. It writes no record, receipt,
artifact or request reservation. A request ID that is already recorded
returns its recorded receipt. An operation whose preparation acts outside
the store (an execution, a review dispatch, PDF rendering or git) refuses
`--check` with `check_unsupported`. A later real write validates
everything again. A refused write on a large store costs a full write, so
a study can now find the refusal first without that cost.

An audit of the 87 commands that accept `--check` found 71 that reach
their first refusal or acceptance without a disk write, 16 that refuse
`--check`, and none that writes. A test runs `--check` for every command
and compares the whole workspace tree before and after.

## Upgrade notes

The bytes of the three Codex transports changed, so they enter a new
runtime. A Codex route recorded before 0.66.0 is refused for new reviews
and probes with `review_route_runtime_stale` until a new route is recorded
and probed under 0.66.0. Reviews bound earlier stay verifiable against
their own routes.

## Choices for the owner

- Code mode: five feature settings stop code execution. The open question
  is whether a call of the disabled `exec` that ran nothing may count as a
  notice instead of making the attempt unverified; this release keeps it
  unverified.
- Standard error output: a bounded tail (20 lines, 4,096 bytes) on failure
  only. The alternative keeps the whole output as an artifact.
- Check mode: one flag on every mutating command, with explicit refusal
  for operations that act outside the store. The alternative is a
  separate command per operation.

## Known gaps

- The reviewer prompts do not yet ask the reviewer to call no tool, and the
  agent-facing texts of the check mode are not written (text author).
