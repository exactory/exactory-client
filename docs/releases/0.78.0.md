# Exactory 0.78.0

This release keeps a session working when the plugin's file guard cannot check a tool call. It follows 0.77.0. It
is phase A of the work recorded in `misc/harness-improvement/20261106085323-override-of-harness-stops` of the
exactory repository. GPT 6 Astra at effort `xhigh` reviewed the design, and the owner authorized the implementation
on 2026-11-06.

## Why

- The file guard runs on every tool call that the host reports to its `PreToolUse` hook. When one of its own checks
  failed, for example on a conflicting entry in the discovery registry or on a directory without read permission,
  it denied the call. This denied every call that reached the guard, reads included. The agent had no way to read
  the record or to run a command through the hooked tools.
- Each such denial named the error, and the denial of an unexpected error asked that it be reported to the user.
  Only the two controller-read messages named a runtime to use. No denial said what still ran, and none named a
  host control that lets the session go on. On 2026-10-23 a conflicting root identity denied every tool until the
  owner moved the session out of the record.

## What changed

- When the guard cannot check a call, it decides by the call alone. A call passes when every item of it is a
  read-only tool (`Read`, `Glob`, `Grep`, `WebSearch`, `WebFetch`, `ToolSearch`) or a shell command made only of
  the bare names `cat`, `ls`, `grep`, `head`, `tail`, `wc`, `echo` and `du`, joined at most by `;`, `&&`, `||` or
  `|`. That check reads characters, not shell syntax. It rejects a newline, `$`, a backtick, an assignment, a
  redirection, a token with a parenthesis or a brace, and an argument with `*`, `?` or `[`, also inside quotes. A
  Codex batch passes only when every item of it passes. An empty batch is denied on this path only.
- `rg`, `printf` and `pwd` are not in that list, because some of their forms start another program or assign a
  shell variable.
- Every other call is denied. The reason keeps its diagnostic and ends with three things: what still passes, the
  instruction to tell the user which call was denied and to quote the diagnostic, and the controls that only the
  user has. With `/cd <path>` to a directory outside the workspace that holds the record, unrelated work continues.
  Any other call that names the record stays denied, and so does a session whose directory is still inside that
  workspace, for example in the parent of the record. Codex changes directory only in an idle primary session with no queued
  input or background terminals, and Claude Code can restrict `/cd` targets by permission rule. To work in the
  record, the user disables the plugin: on Claude Code with `/plugin disable exactory@exactory-ai`, then
  `/reload-plugins --force`, because a pending plugin change reaches the running session only through a reload, and
  on Codex by disabling the Exactory hooks in `/hooks`. A plugin that an organization manages or requires, and a
  hook that an administrator manages through `requirements.toml`, cannot be disabled this way. The denial of an
  unsupported managed payload or shell command, and the Codex adapter's denial of a patch that it cannot read
  (`[exactory] Cannot check this patch: ...`), end with the same statement.
- A definite finding keeps its denial, without that statement: a write to a file that the harness owns, a write
  into `final/` or `intermediate/`, and a write to what the search controller owns.
- A payload that is not valid JSON, or that does not normalize, is denied as before. The guard then has no items
  to decide by.
- `skills/math-solver/SEARCH.md` and the docstring of `hooks/guard_attack_files.py` describe this behavior. The
  replay test of the math hooks now expects a read-only `exec_command` to pass when the installed controller cannot
  read the record.
- The regression ledger has a new `real_shape` entry, `override-guard-cannot-check`, with 22 tests. They include
  the scenario of 2026-10-23. The over-long path of 2026-11-03 keeps its entries from 0.71.4 to 0.71.8.
- Known limit: the managed Codex hook runtime of 0.75.0, which an administrator installs, runs its dispatcher before
  any hook of a release. When the dispatcher refuses the call, for example because the session has no binding or
  its release is not approved, it prints `[exactory-runtime]` and the reason to stderr and exits with status 2 on
  `PreToolUse`, which Codex reads as a block. No hook of the release runs then, so the read-only passage does not
  apply. The dispatcher changes only through a reviewed protocol migration, which is outside this release.

The content of stored records does not change, and no migration is necessary. `hook_runtime/` is unchanged.

## Checks

- The 24 test modules that name a changed file pass on Python 3.12.8 and 3.9.6 with 789 tests each.
- After that run, one word of the guidance and one test changed. The seven modules that pin them pass again on both
  versions with 119 tests each: the guard, replay, ledger, release-records, guidance, manifest and Codex modules.
- `codex/generate.py --check` and `git diff --check` pass. `hook_runtime/` and the protected modules are unchanged.
- GPT 6 Astra at effort `xhigh` reviewed the guard before this release and found calls that passed as read-only but
  could start a program or assign a variable. They were reproduced and fixed, which is why `rg`, `printf` and `pwd`
  are out of the list.
