# Exactory 0.88.1

This release removes a store validation that 0.88.0 added before every command with a payload file. It follows
0.88.0. The failure and the fix are recorded in
`misc/harness-improvement/20261113110022-every-open-record-and-review-capacity` of the exactory repository (lane
store-validation).

## Why

0.88.0 records every payload file path in its workspace-relative form. For that change, the command line read the
committed receipt of the request before it prepared a command whose payload names a file, also when the request was
new. The read opened a second store and validated the full history and the structure of the store once more. An
artifact registration then made three full validations of the history instead of two. The CI of 0.88.0 failed the
test `test_register_artifact_with_two_full_validations_and_one_structural_check` on Python 3.9, 3.12 and 3.14 with
`3 != 2`. No stored record changed, and every command gave the same result as before. Only the extra validation
work was wrong.

## What changed

- A command with a payload file first admits its paths in the usual way. The command reads the committed receipt of
  its request only when a path is refused with `unsafe_path`, so that a repeat of an earlier request can still
  replay its original payload when the path of its input has since become a symbolic link inside the workspace.
- The receipt is read only when the workspace exists. In a folder that is not a workspace, a refused path keeps the
  refusal `unsafe_path`.
- `import-response` keeps the receipt read that it made before 0.88.0, and check mode is unchanged.
- An artifact registration again makes two full validations of the history and one structural check. A new test
  pins the exact validation sequence of 40 commands with a payload file, with relative and absolute paths, and
  their existing refusals. A second test replays an artifact registration after its input was removed.
- Incident ledger entry `payload-path-admission-repeats-store-validation`.

## Compatibility

No route-pinned file changes, and no reviewer route becomes stale. Stored records keep their meaning. The refusal
codes and messages are unchanged.
