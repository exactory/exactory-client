# Exactory 0.50.1

This release adds to 0.50.0 the literature repairs and the store bounds of the
v11 harness record (tasks H2, H3, H6 and H13), which 0.49.0 left out. It also
makes `exactory-derive` report more inputs without a Python traceback. The
repair of the math-solver attack guard (task H15) is not in this release.

## A replaced search judgment no longer owes full readings

Each work that a search judgment cites becomes a critical full-text requirement
(purpose `novelty`). Before this release, the requirement stayed after a new
search for the same purpose replaced the judgment. So a study owed full
readings of works that no current judgment cited.

- The requirement of a cited work now counts only while its judgment is the
  selected search of its profile and purpose. A new search for the purpose
  retires the requirements of the works that it does not cite again. The
  stored requirement records stay.
- A source deferral and the foundation digests hold every requirement record of
  a version while the version is a required full text. A version is a required
  full text while one of its own records counts, or while the citation graph
  places it at Tier 1 or 2. So a deferral that an earlier release recorded
  stays active after the upgrade while its version stays required.
- A replacement can make the judgments of other purposes stale. A new search
  for a purpose can drop a family that only the replaced judgment required.
  Then each selected judgment of another purpose that was recorded while the
  family was required reports `search_frontier_stale` and
  `search_evidence_stale`, until it is recorded again. These are notices under
  `lineage-v1` and `sampled-v1`, and obligations under `exhaustive-v1` and
  `screened-v1`. A judgment that found a version of the family reports only
  `search_frontier_stale` if the citation graph had read no reference of the
  family's versions when the judgment was recorded. The `search` row of the
  [CLI reference](../research-cli.md) gives the complete rule.

## A citing-works capture binds its OpenAlex filter

- `filter` is now a query parameter of a native OpenAlex capture. So a
  citing-works capture (`filter=cites:W123`) imported with provider `openalex`
  records a `recent` search. Before, `search` refused it, and the capture had
  to be imported again as a `web` capture.
- The query of such a response is the whole filter value: `cites:W123`, or
  `cites:W123,from_publication_date:2025-01-01` when the filter also holds a
  date clause. The literature-review skill now says so.
- The bounded loop of `lineage-v1` now counts each captured query once. Before,
  it counted the distinct query strings of the searches of a purpose. A native
  capture now counts by its provider, its endpoint and the parameters that
  decide which works match. Its pages, its repeated captures and captures that
  differ only in another parameter, such as a sort order or a `mailto`
  address, count once. Captures whose matching parameters differ count apart,
  even when they share a query value. The `loop-close` row of the
  [CLI reference](../research-cli.md) lists the parameters of each registry and
  how URLs that spell one query differently are compared.
- A `web` or `mcp` capture counts by its saved response and its bound query. It
  adds no query when a native capture of the same purpose was bound to the same
  value.

## The citation graph reads one bundle for each original

Before this release, the citation graph read the reference occurrences of every
bundle of a version. A new bundle for the same paper added its own occurrences,
and the occurrences of the earlier bundle kept their obligations, such as
`reference_identity_ambiguous`.

- For each acquired original of a version, the graph now reads only the
  selected bundle. This is the latest bundle of that original, unless the last
  `bundle` import of the version named an earlier one. The graph always reads
  the occurrences of registry observations.
- The graph reads a bundle of another body only while no acquired original of
  the version has a bundle. Another body is, for example, a passage on a saved
  tool response, or an original that another bundle links as a supplement.
- A verification target reads the bundle of each acquired original, whatever
  its pin.

## Stored values that every supported Python reads back

Python 3.9.6 converts an integer of any length, but Python 3.11 and later
refuse to parse an integer of more than 4300 digits. A deeply nested value can
also exceed the recursion limit when the store is read. Before this release,
the store wrote such values. Python 3.11 and later then failed to read a store
that held such an integer, and a value nested several hundred levels deep made
the guarded snapshot of the store fail.

- The store refuses to write a payload, a record or a result that nests more
  than 100 levels or holds an integer of more than 4300 digits. The mutation
  fails with `invalid_input` and does not change the revision. Reads, and
  retries of committed requests, do not check these bounds, so a store that an
  earlier release wrote stays as readable as before.
- An `exactory-research` payload file, and the verdict body that
  `bind-verdict` names, nest at most 32 levels. A run's metric has had this
  bound since 0.48.0. Later records and reviewer exports hold copies of the
  values of an input deeper than the input holds them. A reviewer export counts
  at most 40 levels, and the deepest copy that it counts is 8 levels deeper
  than its input. The deepest copy found in a record is 12 levels deeper.
- A `review-assignment` of a paper review (role `manuscript` or `standalone`)
  repeats the stored bundle of `manuscript` in `context.bundle`, and the
  assignment requires that bundle to equal the stored record. So the bound
  counts the rest of that payload and not the bundle.
- A deeper input, or an input with an integer of more than 4300 digits, fails
  with `invalid_input`, and the message names the refused input. The check
  runs before `init`, `adopt` or an acquisition creates a store.
- Three fields that take a finite number now refuse an integer beyond the
  float range (about 1.8e308), each with its own error:
  - the `timeout_seconds` of `bind-run` (`invalid_execution`),
  - a number of a PDF locator region (`invalid_locator`),
  - the usage `wall_seconds` of `read-batch` and `screen-batch`
    (`invalid_batch`).

  Before, these values ended the command in a Python traceback, or
  `wall_seconds` was charged to the account.
- A charge that adds a float to an integer beyond the float range, in either
  order, fails with `invalid_input` and changes nothing. Before, it ended the
  command in a Python traceback. A charge that makes an account total an
  integer of more than 4300 digits fails in the same way. Integer charges
  within that bound are recorded as before.

### Records that an earlier release wrote

An earlier release did not check these bounds. So a store that it wrote can
hold a value outside them, or a value that fits its own record but not a later
copy. A new payload, record or result that copies such a value fails with
`invalid_input`. These cases are known:

- A run that exactory-client 0.47.0 or earlier claimed has no bound on its
  metric. If the metric nests more than 98 levels, `reconcile-run` of the run
  without an observation fails. The run then has an outcome but no
  observation, and its strategy admits no further run. A new `reconcile-run`
  request for such a run that an earlier release observed fails if the metric
  nests more than 99 levels. `manuscript` fails if it cites a result of the run
  whose metric nests more than 95 levels.
- Under Python 3.9.6, an earlier release accepted a seed of more than 4300
  digits. A launch, a `reconcile-run` or a `manuscript` that copies such a seed
  fails.
- `bind-verdict` of an earlier release accepted a verdict body of more than 32
  levels. For such a body of 98 levels, `exactory verify` sends the verdict, but
  the store cannot record the response, so `exactory reconcile` fails with
  `verdict_reconciliation_pending`. A later `exactory verify` then sends the
  verdict directly, with a `Managed record skipped` line. How the server
  treats that second request is not known.

The [CLI reference](../research-cli.md) gives each case: "Actual execution" for
runs and seeds, and the `bind-verdict` row for verdict bodies. A scan of 133
stores on the maintainers' machine found no payload deeper than
17 levels and no integer of more than 101 digits.

## exactory-derive

- A steps file that nests more than 32 levels fails with exit code 2, and no
  step is checked. A steps file needs 4 levels. On the Linux test runner,
  Python 3.14.7 parsed a steps file nested 100,000 levels, where Python 3.9 to
  3.13 raise `RecursionError`. With this bound, every supported Python refuses
  the same files. A steps file nested beyond the recursion limit of the
  interpreter also fails with exit code 2. Before, it ended the run in a Python
  traceback.
- A malformed step is `unparseable` and is not checked. A step is malformed
  when it is not an object, when its `vars` is not a map, or when a range is not
  `[low, high]`. Before, a malformed step ended the run in a traceback.
- A range bound that Python's `float()` cannot convert, such as a word or an
  integer of more than 309 digits, makes its step `unparseable`. Before, it
  ended the run in a traceback.
- A sampled point at which a side has no finite value is skipped, and a step
  with no other point is `unparseable`. Before, such a point never showed a
  difference, so a wrong step was reported `consistent`. An example is
  `x*x = 0` with `x` in `[1e200, 1e201]`.
- `csqrt` and `cexp` now give complex values. Before, every call of them ended
  the run in a traceback, because their result was converted to a float.
- A complex side is measured by the larger absolute value of its real and
  imaginary parts, and a witness gives a complex side as `{real, imag}`.
  Before, a complex witness ended the run in a traceback. A function of real
  numbers that gets a complex value, such as `sin`, now makes its step
  `unparseable` instead of ending the run in a traceback.
- An expression nested beyond what the parser or the evaluator handles makes
  its step `unparseable`. Before, it ended the run in a traceback.

## Upgrade effects

These effects were measured on copies of ten stores on the maintainers' machine
(seven studies and three verifications). Each store was read with 0.50.0 and
with this release.

- In eight stores, the citation graph reads 20% to 75% fewer reference
  occurrences. It no longer reads replaced bundles, and in two stores fewer
  families are at Tier 2.
- In five stores, the number of full-text requirements that count fell by 9 to
  22.
- In two stores, the graph has fewer Tier 2 families (8 to 7, and 13 to 9), and
  the frontier digest changed. In both stores, every selected search judgment
  was already stale before the upgrade.
- In two stores, the `reference_unresolved` obligations fell (46 to 38, and 4
  to 1).
- No source deferral changed its status. No loop state, loop closure or
  staleness of a search judgment changed.

## Known limitations

- The math-solver attack guard reads the words of a command, as the release
  note of 0.49.0 describes. Its repair (task H15) is not in this release.
- The scoped readiness export parses a string value that is whole JSON text and
  reads it one level deeper. So a string that holds JSON can make
  `export --kind readiness` fail with `invalid_scientific_delivery` at any
  input bound (task H16). Releases 0.49.0 and 0.50.0 behave in the same way.
- When a pending capture answered 404 instead of failing on the network, the
  scoped readiness export refuses it with `private_mixed_artifact_required`
  (task H17). The cause is not yet analysed.
- A later payload can cite an accepted value deeper than its record holds it.
  For example, `review` cites each evidence reference of the candidate one
  level deeper than `result.evidence` of an assessment holds it, and a
  `value-review` holds such a support assessment one level deeper again. So an
  assessment whose deepest value in `result.evidence` is at level 31 leaves no
  room for its `value-review`.
- A copy of an input of 32 levels reaches exactly the 40 levels that a reviewer
  export counts, so the input bound leaves no margin there.
- The depth analysis did not check the values of files that a payload only
  refers to, other than the verdict body.
- In `exactory-derive`, an evaluation error at one sampled point still makes the
  whole step `unparseable`, as before.
- The limitations of the math-solver launch that the release note of 0.49.0
  lists remain.
- Tests with short run timeouts or fixed time windows can fail on a heavily
  loaded machine, as in 0.49.0.
