# Exactory 0.67.0

This release resolves the open records of `misc/harness-improvement` of the exactory repository in one release.
The work is recorded in `misc/harness-improvement/20261029205602-release-0-67-0-every-open-record`, and each source
record names what shipped in its "Release state" section. Design ran on gpt-6-astra at effort xhigh, the
implementation lanes on gpt-6.1-sol at effort xhigh, the agent-facing texts on Claude Fable 5.1 at effort max, and the
lanes that the Codex budget did not cover on Claude Opus 5.5.

## Reviews and their evidence

- A review observation survives a busy store (T9 of `20261027085554-bar-source-requests-exceed-route-capacity`).
  The finishing write of a reviewer call (`review-probe`, `review-run` and `review-output-correction`) retries only
  `store_busy` and `stale_revision`, at most 600 attempts within 600 seconds. It never calls the model again. The
  harness keeps the observation only in the process that called the reviewer and writes no file for a later process
  to read it from. A file in the workspace is no evidence of what the reviewer returned, so the harness never
  completes a pending invocation from disk. A retry of a pending request refuses with `review_invocation_pending`,
  as before 0.67.0. The other writes that follow completed outside work (acquisition and cohort pages, execution
  prelaunch, outcome, observation and reconciliation, probe origins and pins, remote responses, submission
  observations, publication read-backs) retry only the same two refusals, at most eight attempts within eight
  seconds. Every attempt computes its change from the current records. The unbounded stale-revision loops of the
  probe paths are bounded now.
- A call of the disabled Codex `exec` tool that ran nothing is a notice (the owner's decision of 2026-10-28, record
  `20261027070717-codex-code-mode-tool-unverifies-review`). When every tool call of a Codex rollout is `exec` and every
  tool output is exactly "code-mode host is disabled", the issues `tool_call:exec` and `unknown_or_tool_input` are
  removed and each call is kept in `context_evidence.notices`. Any other tool call still leaves the attempt
  unverified. The transport modules are unchanged.
- Every recorded result output reaches its reviewer (Verify-D1 of the verification of 0.66.0). Packet evidence is
  keyed by the exact descriptor instead of the SHA-256, so an alias no longer hides the readable descriptor of a PNG
  result; reconciliation keeps each output's admitted media type; an opaque binary result output goes to the HTTPS
  route as base64 JSON (`inline-result-bytes`), and text-only routes keep omitting binary bytes explicitly.
- A refused review output names the failed rule and the item (T10 of the bar-source record). The refusal record and
  the `review-run` receipt carry the validator's message, the JSON Pointer of the failed field (`details.path`), the
  request id where the item has one, and the measured limits of a failed length or range check. A malformed reading
  response stays refused as a whole, and earlier refusal records with `details: null` stay as recorded.
- New reviewer prompts open with a versioned common text (record
  `20261024202815-claude-route-emits-two-json-objects`, T2, and the instruction to call no tool). New assignments name
  `parameters.common_version = 2`: the packet is the only evidence, call no tool, one JSON object with no prose,
  example or code fence, and the `RETRACTED` correction form that the Claude route reads. An envelope without
  `common_version` keeps version 1, the text of 0.55.0 to 0.66.3. The 126 supported prompt envelopes of 0.66.3,
  frozen in `tests/fixtures/review-prompts-0.66.3.json`, verify with their recorded bytes, and the common text does not
  change which scientific contract a prompt has.

## Check mode and workspaces

- Every writing command has a check mode that writes nothing (a bug hunt on 0.66.0 found `strategy-packet` without
  `--check`). Of 158 subcommands of `exactory-research`, `exactory-math`, `exactory-lab` and `exactory-draft`, 51
  writing commands lacked `--check`: `exactory-lab state set` and `decide` and the native search commands `pause`,
  `side-interval`, `retreat`, `interpret` and `render` now run the store check, and the other 44 refuse with
  `check_unsupported` before any effect. A native check creates no lock file, directory or event, and native reads
  create no directory. A test derives the command list from the parsers.
- Malformed payloads refuse with a structured error (Verify-D5, Verify-D6). A readiness review accepts the optional
  strict boolean `author_memory_notes_present`; `reconcile-run` validates its payload before it takes the execution
  owner; cohort selection, publication-scope selection and response imports check their identifiers.
- `exactory-lab run` and `decide` work in a problem record (T8 of the bar-source record). `run` finds the record's
  research store as `probe` does; `decide` needs an explicit `--stage` outside a study; `state show` and `state set`
  stay study commands.
- The draft-marker obligation names a step that works in every state (v13 T13). A symbolic link, a directory or a
  marker that adoption refuses is moved aside first instead of being sent to `adopt`, and a completed study is sent
  to `exactory-draft init` instead of a same-stage update that checks the completion gate. Each state has its own
  explanation of at most 120 characters.

## Math-solver openness reading chain

A math-solver result review that binds an openness minimum was refused when its packet exceeded the route: the
triangle-free objective exported a packet of 2,764,871 bytes, and `review-run` refused it with
`review_input_too_large` (record `20261024210650-math-solver-openness-packet-exceeds-route-input-limit`).

- Such a review, for a checkpoint or for the objective's closure, is read as a chain on the reading engine of 0.66.3
  under the new protocol `exactory-openness-reading-math-v1`. The units arrive in this order: the captured responses of
  the bound searches, the extracted main texts whose originals the bound readings' source bundles pin, then the bound
  search and reading records. Every turn delivers at most 120,000 characters of new unit text and fits its route. A
  final-turn reading response needs a passage request that delivers characters within the remaining allowance.
- The controller resolves an attestation that names the first turn to the chain's terminal turn (a failed turn that a
  new run replaced is history; a second live continuation is a fork), checks every turn and the delivery of every
  unit, and stores the derived `reading_turns` receipts on the acceptance or the closure; audits compare them.
- On a fixture of the recorded size (2,764,871 bytes) the chain reaches a final assessment, an acceptance and an audit
  in 28 turns on both routes. The final request is 708,933 characters on the Codex route and 1,221,328 on the Claude
  route. The text-priority approach of an earlier unreleased lane is not used.

## Review before the merge

An Astra code review of the release branch found four defects, and each is repaired with a test that fails without
the repair:

- A retry of the same request recorded a fabricated answer from a sidecar file under `research/review-observations/`
  as an instrumented attempt. The harness now keeps a review observation only in the process that
  called the reviewer (see the first item of "Reviews and their evidence").
- The activity hook wrote `activity.jsonl` for a native `--check`. A harness command with `--check` leaves no entry.
- `search render --check` accepted a dangling symlink at a generated view while the write committed its event and then
  failed. A symlink at a generated view now refuses the operation before anything is recorded.
- An import recorded family-conflict diagnostics of an older snapshot when its finishing write retried on a later
  revision. An import keeps the revision of its snapshot, as in 0.66.3.

The full suite of the release branch also caught a help text: argparse reflowed the `exactory-draft` description and
broke "exactory-check" across two lines. The help now shows the module docstring with its own line breaks.

## Upgrade notes

- `research_harness/review_transport.py` changed, and the `openai_responses_v1` route pins its bytes. A route of that
  adapter recorded before 0.67.0 needs a new route and probe for new reviews; its recorded attempts stay verifiable
  against their pinned runtime. The Claude and Codex transport modules are unchanged, so their routes stay current.
- A store or record written by 0.67.0 can hold assignments whose prompt names `common_version` and refusal details
  that earlier releases do not know.

## Known limits

- A check of `init` or `problem-init` in a directory without a store refuses (`migration_required` outside a
  workspace, `store_missing` in one) while the write succeeds. Check mode exists to find a refusal before an expensive
  write on a large store, and a first `init` writes an empty store.
- A review observation is not recovered by a later process. When the store stays busy for more than ten minutes
  after a reviewer call, the invocation stays pending, as before 0.67.0.
- A math reading chain's requests grow by about 1,000 characters per turn, so a minimum of any size is not guaranteed
  to fit; a final request that still exceeds its route is refused with the size of each part.
- Storing each evidence value once (v15, schema 2) is not in this release. On a copy of the store of study 2409.17337
  the prototype measured a file 49.3 % smaller and 58.5 % more CPU for one write, single samples. Schema 2 rewrites
  the physical history, so the owner decides on its adoption separately.
