# Exactory 0.68.0

This release separates the outputs of every process into two folders that the harness generates in the workspace
root. `final/` holds the current result of each step, and `final/history/` holds the results that a later record
superseded or that lost their standing. `intermediate/` holds every other output, item by item, with its status. The
rule applies to math-solver, ai-science and math-conjecturer, and the owner set it on 2026-10-30. The work is recorded
in `misc/harness-improvement/20261030172848-separate-intermediate-and-final-outputs` of the exactory repository.

## Why

Before 0.68.0 the harness kept every reviewer request, response and output only as digest-named files in
`research/sources/objects/`. Only the SQLite records showed which output a record adopted. Sessions therefore wrote
tools that copied every turn output into one folder. On 2026-10-30, `reviews/outputs/` of the unknotting record held
133 files (2,092,391 bytes). Twelve of them were outputs that a record adopted. The others were reading turns, source
requests, failed runs and empty outputs, and the file names did not show which was which: `assign-openness-astra-1.json`
was the first reading turn of a chain, not its result. The KMP and Sidorenko records have the same kind of folder.

## Two generated folders

`final/` has these parts:

- `reviews/<role>/`: the recorded reviews that count now (`bar`, `slate`, `result`, `adjudicator`, `readiness`,
  `scoped-readiness`, `manuscript`, `prediction`, `round`).
- `problem/`: the selected statement and the latest slate, attempt, openness finding, value, assessment, decision,
  formal checks and post, and the problem exports in `problem/exports/`.
- `study/`: the current round admissions, round decisions and assessments, research decisions, cycle assessments,
  contribution analyses, checkpoints and receipts, the selected and the deposited manuscript bundles with their pinned
  files in `study/manuscripts/<bundle id>/`, and the deposits with their uploaded files in
  `study/deposits/<intent id>/`.
- `verification/`: the current verdicts and tasks.
- `math/deliveries/`: the delivered native attempts and closures.
- `math/<rel>/`: the results that the math-solver controller relies on. `<rel>` is the path of the controller root
  from the workspace root, `attack` in the default layout.

`final/history/` has the same layout. A bar whose slot was repaired, a reassessment that a later one replaced, and the
attempts that an earlier delivery pointer named are examples.

`intermediate/` has these parts:

- `reviews/<role>/<root assignment id>/`: one folder for each reviewer series. `series.json` lists every turn and
  every run with its status, error, usage, refusal and correction, the selected run, and the record that adopted the
  turn. `<NN>-<assignment id>.<run id>.json` is the output of one completed run of turn NN.
- `reviews/routes/` (route probes) and `reviews/packets/` (exported review packets).
- `problem/candidates/`, `lab/probes/<probe id>/probe.json`, and `lab/runs/<admission id>/` with `run.json`,
  `result.json` and `log.txt`.
- `study/`: the bundles that were neither selected nor deposited, `score-history.json` (every recorded manuscript
  review in recorded order), and the remote intents and observations.
- `checks/`: copies of the citation and derivation check reports in `.exactory/`.
- `literature/exports/`, `math/<rel>/` (the controller's runs, checkpoints, proposals that were not admitted,
  invalidated results and one index for each node), and `legacy/`.

Each folder has `README.md` and `index.json`. The index lists every file with its type (`view`, `controller`,
`export`, `legacy`), the kind, id, recorded revision and status of its record, and every file that the harness did not
write under `unowned`. The storage keeps its place: `.exactory/`, `research/sources/` and `.search/` are unchanged, and
so are the work areas that records pin (`draft/`, `experiment/code/`, `research/probes/`, `research/runs/`, the
controller root and its node workspaces). The agent keeps its own files in `work/`.

## When the harness renders the views

- Each recording command of `exactory-research`, `exactory-lab`, `exactory-draft`, `exactory-cohort` and `exactory`
  (`submit`, `verify`, `reconcile`) renders the research store's views once, after its last commit and outside every
  store lock. Read commands and `--check` render nothing.
- Each mutating controller command renders the controller's views after the writer lock is released, and so do
  `deliver-attempt` and `deliver-closure`. A controller command also renders the research views of the review store.
  Each managed native `attack.py` command renders once, at its end.
- A render skips when its marker (`.exactory/output-views.json` or `.search/output-views.json`) shows the current
  revision, the event digest at that revision and the installed plugin version. Otherwise it builds the whole model
  from the records, writes only the files whose bytes differ, and removes the owned files that the model no longer
  produces.
- A record whose canonical JSON is larger than 1 MiB is shown as a summary with its size and SHA-256. A run output or
  an artifact of at most 1 MiB is copied, and a larger one is listed by digest. Sealed outputs are never read.
- A render never changes the result or the exit status of a command. When it fails, the command prints one warning
  line on stderr, and `status` and `next` report the advisory below.
- A render never overwrites a file that it does not own. A file in its way with other bytes is reported as
  `output_view_conflict`, and the view is not written until the file is moved.

Measured cost, from single runs on the development machine while other test suites ran, so the numbers show the order
of the cost:

- The store of study 2402.14112 (3,024,842,752 bytes, revision 1144): the first render took 14.6 s on Python 3.12
  and wrote 339 files, 37,572,588 bytes. 21 record files are summaries. Without them, the views were 407 MB. A later
  command that records a shown kind builds the model again, about 12.6 s on this store.
- A copy of the unknotting store (112 MB, revision 707): the first render took 3.1 s on Python 3.12 and 2.1 s on
  Python 3.9. A render after a review commit took about 1.5 s, and a command that records no shown kind 0.02 s.
- The controller of the unknotting record (71 events): the first render took 0.14 to 0.85 s over seven runs. For
  erdos-124 (451 events, 23 nodes) the first render took 2.6 s. There the render adds about 0.5 s to a mutating
  controller command and about 2.4 s to a native command, which replays the controller once.

## The advisory `output_views_stale`

`status` and `next` of `exactory-research`, and `search status` and `search next` of `exactory-math`, carry
`advisories` while the views may not show the current records. The list holds one entry with the fields `code`
(`output_views_stale`), `action`, `reason`, `path`, `error`, `rendered_revision` and `revision`. A field that does not
apply to the reason is null. The research entry also carries `explanation`.

- The research store's action is `exactory-research export --kind outputs`, which renders both folders again and
  returns `{revision, files: {final, intermediate}, errors}`. Its reasons are `not_rendered`, `behind`,
  `plugin_changed`, `history_changed`, `render_failed`, `file_errors`, `marker_unreadable` and
  `shared_workspace_root`. A store at a controller root whose parent also holds a store renders nothing, and its
  reason is `shared_workspace_root`.
- The controller's action is `exactory-math search render`. Its reasons are `not_rendered`, `behind`,
  `plugin_changed`, `history_changed`, `render_failed` and `reserved_controller_root_name`. A controller root named
  `deliveries` renders nothing, because its views would share `final/math/deliveries/` with the research store's
  deliveries. The default controller root is named `attack`.
- No gate reads the advisory. It never changes `ready`, the obligations, `counts` or the next action.
  `status --summary` and `next --summary` add `advisories: [{code, reason}]` only when the list is not empty.
- To find the reason, `search status` and `search next` read the controller's document once more. On a copy of the
  unknotting controller (71 events, 217,982 bytes) that read took 4.5 ms, against 59 ms for the status itself.

## Exports and packets

CAUTION: Do not give `export --kind problem` a destination outside `final/problem/exports/` of the workspace. The
command refuses it with `export_destination_outside_final`. The texts of 0.67.1 and earlier showed
`--destination problem-export`, which 0.68.0 refuses.

- Without `--destination`, `export --kind problem` writes to `final/problem/exports/<export digest>/`. The export
  digest is the digest of all exported files, the value that `problem-posted` records as `export_digest`. The result
  names the directory under `destination`.
- An existing destination that holds exactly the exported files is returned as it is. A destination with other files
  is refused with `review_destination_exists`.
- `problem-posted` ignores the names that start with a dot when it compares the file set of the export directory, so
  a `.DS_Store` file no longer stops it.
- `problem-openness`, `readiness`, `manuscript` and `round` no longer need `--destination`. Without it, the packet goes
  to `intermediate/reviews/packets/<assignment id>/` (`problem-openness`) or to
  `intermediate/reviews/packets/<kind>-r<revision>/`, with `-2`, `-3` and so on when that folder exists. A given
  destination can still be anywhere, so that a reviewer can run outside the workspace.
- `export --kind foundation` writes to `intermediate/literature/exports/` instead of `research/exports/`.

## Other writers

- `exactory-lab run` and `exactory-research reconcile-run` no longer write `experiment/results/<node>.json` and
  `experiment/logs/<node>.log`. The summary stays in `research/runs/<digest>/summary.json`, and
  `intermediate/lab/runs/<admission id>/result.json` and `log.txt` show the summary and the log.
- `exactory-lab init` no longer creates `experiment/logs/`, `experiment/results/` and `reviews/`, and
  `exactory-draft init` no longer creates `reviews/`. An existing `reviews/` folder stays as it is, and
  `experiment/plots/` stays in the layout.

## The guard hook

- The guard hook refuses `Write`, `Edit` and `NotebookEdit` into `final/` and `intermediate/` of a workspace root that
  the harness renders, except `intermediate/legacy/`. Through the Codex adapter, the same rule covers `apply_patch`.
  The refusal names the file and tells the agent to write its own files to `work/`.
- The hook guards only these two folders directly in a workspace root, so `draft/final/` is not guarded. The hook does
  not inspect shell commands. Each render checks the files that it owns.

## Existing records

- No stored record changes, and no migration runs. The first recording command under 0.68.0 renders both folders
  from the existing records. `exactory-research export --kind outputs` and `exactory-math search render` render them
  on request.
- A folder that the tools of a session wrote before 0.68.0, for example `reviews/outputs/`, stays where it is. The
  session that owns the record can move it once to `intermediate/legacy/<original path>/`, and the index then lists
  its files as `legacy`.
- The unknotting record moves its copies after this release. The KMP and Sidorenko records are left to their own
  sessions.

## Both renderers in one workspace root

A math-conjecturer record has its research store in the workspace root and its controller root `attack/` in it, so
both renderers write `final/` and `intermediate/` there.

- The controller renderer owns `final/math/<rel>/`, `final/history/math/<rel>/` and `intermediate/math/<rel>/`. The
  research renderer owns every other path of the two folders, including `final/math/deliveries/` and
  `final/history/math/deliveries/`, except the export folders and `intermediate/legacy/`.
- `final/index.json` lists the controller's index `math/<rel>/index.json` with the type `controller`. Only
  `final/math/<rel>/index.json` and `intermediate/math/<rel>/index.json` count as controller indexes, so an accepted
  artifact named `index.json` is not read as one.
- The series of a native review names the controller's adoption. The research renderer reads it from `adoptions` in
  `final/math/<rel>/index.json`.
- A test renders both views of this layout in one temporary root. It checks that every file has one owner, that each
  index lists only its owner's files, that no file is unowned, that the series shows the adoption, and that a second
  render of each writes nothing. A local check does the same on a copy of the unknotting record. There the first
  render of both took 1.0 s on Python 3.12 and 1.2 s on Python 3.9, and the series named 10 adopted assignments.

## Upgrade notes

- No module that a route pins by its bytes changed, so every recorded route stays valid and needs no new probe.
- A session whose instructions or tools pass `--destination problem-export` to `export --kind problem` gets
  `export_destination_outside_final`. Leave out `--destination`, and read the directory from `destination` in the
  result.
- A session that reads `experiment/results/<node>.json` reads `intermediate/lab/runs/<admission id>/result.json`
  instead.

## Known limits

- Every render that does not skip builds the whole model. On the 3 GB study store that is about 12.6 s for each
  command that records a shown kind.
- A controller command that fails after its commit renders nothing. The replay of that request or the next mutating
  command renders the views.
- The hook compares folder names exactly, so on a file system that ignores case it does not refuse a write to
  `FINAL/x`. The controller compares the reserved name `deliveries` exactly in the same way, so there a controller
  root named `Deliveries` renders, and its views mix with the deliveries.
- The storage itself is not split. The owner did not object to the proposal that `research/sources/objects/` stays as
  storage, and any split of the storage is a separate decision.
