# Exactory 0.56.1

This release repairs four defects that the first problem record met on the
night of 2026-10-21, when it ran its result reviews on the Claude Code route of
0.56.0 and then reached the post gate (`misc/harness-improvement/v19`, T30, of
the exactory repository). The record kinds, the prompts and the packet shapes
of 0.56.0 are unchanged.

## A citation without a digest in the post gate

- The version 2 result prompt of 0.56.0 cites a delivered record as `{kind,
  record_kind, id}`. The post gate's audit of a recorded review against its
  frozen delivery (0.55.1, `review_evidence_undelivered`) reads no stored
  record, so it had no digest to match for such a citation, reported it as
  undelivered, and then crashed on the missing `digest` key
  (`KeyError: 'digest'` from `exactory-research status`, `next` and `gate
  post`).
- Under frozen validation a reference without a digest now binds to the row
  that carried the record of its kind and id; a row that names no id binds
  through the projection's own id. Record-time validation, which reads the
  stored record, is unchanged.
- A reference that no packet carried is still refused, with `digest: null` in
  the refusal detail.

## The review binding of objections and reassessment findings

- `validate_review_contract` validated the evidence of a problem review's
  `objections` without the review binding, so a result reviewer who cited a
  delivered record by kind and id inside an objection was refused with
  `invalid_strategy`. The same omission stood for the findings of a
  context-repair reassessment in `validate_reassessment`.
- Both now validate under the review binding of a problem assignment, as the
  value, assurance and objection-finding arrays already did.

## The Claude Code route

- A model often returns the JSON answer inside one Markdown code fence. The
  route now hands on the answer without that fence and records
  `execution.fence_removed`; the raw result stays in the stream digests, and
  the inspection still compares the raw assistant text with the raw result.
- At effort `max` the CLI emits a `system` event of subtype `thinking_tokens`,
  the thinking-budget accounting of the turn. The inspection accepts it; every
  other system subtype after `init` still invalidates the stream.
- The route gives the CLI its output bound: the child process receives
  `CLAUDE_CODE_MAX_OUTPUT_TOKENS` equal to the route's `max_output_tokens`, and
  the runtime's `output_limit` names that. Without it the CLI stopped a long
  answer at its own default and continued in a second turn, which the
  inspection refuses as an injected input (`incomplete_turn`,
  `tool_or_injected_input`); the first result review of the first problem
  record on this route ended that way after 209,111 output tokens at effort
  `max`. The bound is still checked after generation.
- Live check: both probes of the first problem record verified
  (`verified_for_route`) on `claude-opus-5-5` and `claude-fable-5-1` at effort
  `max` after these two repairs; before them, the first probe failed with
  `JSONDecodeError` and the second with `system_event_thinking_tokens`.

## The earlier packets of a slot's history

- A context-repair packet carries the slot's scientific history with each
  earlier turn's packet. The luna slot of the first problem record (a repair of
  a repaired bar slot) carried eight of them, 4.3 MB, and the input stayed above
  the Claude route limit after every existing elision, so the run was refused
  (`review_input_too_large`). The local routes now have one more reduction,
  applied last and only while the input is still too large: the earlier packets
  give way, largest first, to `{delivery: "packet-elided-route-limit",
  packet_digest, note}`; each turn keeps its observed output and its
  independence, and the record holds every packet.

## The context-repair prompt

- The suffix that a context-repair assignment adds to the role's prompt said
  "Return an additional reassessment object". Three reviewers in a row, on two
  models, closed the role's object and wrote the reassessment after its closing
  brace, so the output was not one JSON object and the run ended
  `review_transport_failure`. A first rewording ("one more member, written
  inside that object") led another reviewer to place the reassessment inside
  `value`. The suffix now names the top-level members of the output and asks
  for `reassessment` as one more top-level member beside `value`. The template
  id is unchanged; the template hash of every `/context-repair` prompt of the
  current version changes; the version 1 prompts keep the earlier suffix
  (`review_context_repair.PROMPT_0560`), so their bytes are unchanged. An
  assignment of the current version recorded with either earlier suffix
  (`EARLIER_PROMPTS`) keeps its verified prompt without becoming a version 1
  prompt, so a bar or result that a context repair installed under 0.56.0 or
  during this repair stays verified with the checks, rubric and bar
  calibration of its template.

## Tests

- Four expectations of 0.55.1 that 0.56.0 did not update now state the 0.56.x
  contract: the result prompt hash; an artifact cited by a historical objection
  reaches the slate reviewer as a reference template with its passage mapping;
  the adjudicator receives a cited reading as the projection the stating packet
  carried, with no artifact descriptor; and a record reference without an `id`
  is the malformed citation, a reference without a digest is the result form.
- New: a result review citing a record without a digest passes the frozen
  audit; an uncarried record is refused with `digest: null`; the fence removal;
  the thinking-token event.
