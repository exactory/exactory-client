# Exactory 0.64.0

This release repairs Claude review delivery and the binding of standalone
proposal reviews. Allocated side work runs before root finalization, and
admission fills missing attack files. Activity logs distinguish harness
sessions, and hooks name the runtime that wrote an unreadable record. These
are the seven math-solver lanes merged on top of 0.63.0.

The implementation, choices and evidence are recorded in
`misc/harness-improvement/20261026230912-math-solver-repairs-0-64-0` of the
exactory repository. `TASKS.md` names each lane and its source record.

## Claude route notices and earlier reviews (route-review)

The Claude route accepts a basic `ui_invalidate` render notification as a
notice. Its fields are exactly `type`, `subtype`, `event`, `uuid` and
`session_id`, with `event` equal to `ui.render` and nonempty identifiers.
Every accepted occurrence stays in the context evidence. Extra fields,
including `prompts_screened` and `instances`, and unknown system subtypes
remain issues that prevent context verification.

An `api_retry` event with the exact basic schema of Claude Code 2.1.310
also counts as a notice. The stream must prove one successful generation
with one turn and a final result whose output and usage match the response.
Missing or extra fields, the optional `no_response` payload, invalid usage
and additional results remain issues. A retry notice never removes another
context issue.

Attempts and probes authenticate against the runtime pinned in their route
record. A later adapter change no longer invalidates an earlier bound
review. New runs and probes refuse a route whose pin differs from the
installed adapter, before a provider call or an invocation record.

The legacy rule covers the issue-only attempts that the Ferrers objective
bound under its local repair. It requires a route pinned to the Claude
adapter released in 0.60.0 through 0.63.0 and the issue list exactly
`["system_event_ui_invalidate"]`. Every other provenance and context check
still applies. The rule applies to matching pinned adapters and evidence
across objectives. It never promotes a failed probe. Those historical
streams were not retained, so the rule does not establish their UI fields.

The response retains each system event's original bytes, in order, up to
4,096 events and 4 MiB. It records the bounds, counts, digest and
truncation flag, and continues to inspect the entire stream after retention
stops. `inspect_retained_system_events` classifies the retained events
again without the CLI or changes to the recorded result. A retained prefix
cannot establish the contents of omitted events or replace authentication.

## Explicit withdrawals in Claude answers (route-json)

The Claude route can recover the final object from an answer with several
complete JSON object blocks. Each withdrawn block must have one following
line that contains exactly `RETRACTED`, at column zero, outside a fence.
Only answer blocks, those marker lines and blank lines are accepted. Prose,
examples, arrays, indented blocks and unmarked corrections cause refusal,
including the unmarked correction in the original incident.

Each object starts at column zero and ends on its final line without other
text. A fenced block contains exactly one object. The opening line is
exactly three backticks, alone or immediately followed by `json` in any
letter case. The closing line is exactly three backticks. Blank lines
can surround the answer, the markers and the object inside its fence.

The response keeps the whole original text and its digest with
`self_corrected: true` and `retracted_object_count`. The ordinary output
checks apply to the final object. An invalid final object causes refusal,
with no fallback to an earlier object. Recorded responses replay their
saved output without this parser running again. The Codex routes keep their
existing refusal of answers with multiple objects.

## Proposal reviews after an unrelated finish (review-context)

A standalone proposal review stays bindable after an unrelated node
finishes. The exception requires an independent proposal anchored to the
objective and a new budget. It excludes native parents, predecessors,
equivalent nodes, inherited evidence or assumptions, claim assumptions and
computation dependencies. Only an unrelated node's change from `admitted`,
`active`, `waiting` or `result_ready` to `finished` qualifies. Its earlier
status and corresponding strategy inventory remain valid. Every other
packet field, scientific evidence item and reviewer binding stays exact.

The binding records `context_drift`, with each changed path and its earlier
and current values. It preserves the reviewer output and digest. Strategy,
result, recovery and root-closure reviews keep their strict context checks.
A new assessment still invalidates an earlier proposal packet.

Packets compare as canonical JSON bytes, so `1`, `true` and `1.0` are
distinct. Every new `review` and `reassess` binding validates its packet
afresh, even with an output that already has a binding. Each binding with
permitted drift records its own receipt. Historical audits and retries of
the same request keep their recorded meaning, and a refused binding writes
no native event.

## Allocated side work and root closure (side-interval)

An allocated, unexhausted side interval runs its ready standalone node
before `finalize_root` while final review remains pending. Finalization
keeps priority over standalone work without an allocation. Reconciliation
and result preparation retain their earlier priorities, and the interval
adds no root proof coverage or resource allowance.

`search complete` refuses with `standalone_closure_pending` until every
admitted standalone node finishes or retreats. This applies even without an
interval, and includes waiting, suspended, exhausted and deferred work. The
refusal names every blocker, and `status` and `next` report
`closure_blocking_node_ids`. Imported history does not count as admission.
Earlier completed records and the draft's standalone `begin` events replay
unchanged.

## Missing attack files at admission (admission-skeleton)

Admission completes the skeleton of an existing attack directory. It
creates the missing directories `deterministic/`, `units/` and `study/`.
For absent files, it creates an empty `journal.jsonl` and `novelty.md`, and
the initial `problem.json`. Existing file bytes stay intact. Existing
research with a nonempty journal still needs explicit adoption.

`search reconcile` repairs an earlier admitted root with no initialization
effect and no journal. If that missing journal has recorded
moves, reconciliation refuses with `recovery_conflict`. Native commands
that find a missing journal inside a managed root name the incomplete
admission skeleton and `search reconcile`. Interrupted initialization uses
the existing request retry or `search render` recovery, with conflicting
bytes refused.

## Activity for harness sessions (activity-log)

An ordinary shell call enters an attack's activity log only after the log
contains a harness-command entry for the same host and session. Harness
commands and Write or Edit calls under the workspace still enter the log.
New entries carry `session_id` and `harness_command`. Inspection by a
session without that harness entry leaves `activity.jsonl` byte for byte
unchanged, including at the 200-entry cap.

`status` shows the latest identified harness session's retained entries.
Logs without such an entry keep the old view. A harness command on another
attack does not establish membership for this attack. If parsing fails, the
recorder omits the entire call. Activity remains advisory and grants no
controller work or proof credit. The guard keeps its existing command
checks.

## The runtime that wrote an unreadable record (hook-replay)

After initialization or a new event commit, the controller writes
`.search/writer-runtime.json` atomically under its writer lock. This file
records the plugin version, a digest of the controller and harness sources,
and the launcher. Reads, refused commands and repeated requests do not
refresh it. The controller computes the identity once per process.

When a record fails to replay, the hooks compare its writer with the
installed runtime. A different writer gives a refusal that names both
runtimes and the command for the recorded launcher. An unknown writer gives
a refusal that says the installed controller cannot read the record. Only a
failure under the record's own writer keeps the recovery message. The guard
keeps its refusal, reads stay exempt, and the Stop hook uses the same
classification.

The file records writer identity without changing the `tree.json` envelope.
A crash between the tree commit and the identity write can leave the
previous writer named, or no identity after initialization. A repeated
request does not repair that identity because it commits no event.

## Upgrade notes

For a Claude route recorded before 0.64.0, record and probe a new route
under 0.64.0.

The Claude review adapter's bytes changed. New reviews and probes against
an older Claude route fail with `review_route_runtime_stale`. Reviews bound
earlier stay verifiable against their own routes.

A plugin older than 0.64.0 cannot read an event that carries
`context_drift`. Records written by 0.64.0 keep the `tree.json` format of
0.63.0. The separate writer file does not change that format.

## Choices for the owner

These choices ship as provisional behavior. The owner's merge of the
release pull request accepts them.

- API retries: an exact basic `api_retry` event counts as a notice only
  with proof of one generation and matching output and usage. Alternatives
  keep every retry an issue or admit the optional `no_response` schema
  under a separate exact rule.
- Retention: the response retains system events up to 4,096 events and
  4 MiB of original bytes, with a truncation flag. Alternatives retain
  the entire stream, use different limits, or refuse an invocation that
  exceeds a limit.
- Answer recovery: option B recovers the final object only after an exact
  `RETRACTED` line for each withdrawn object. Option A refuses every answer
  with multiple objects and keeps the single-object prompt and existing
  retry.
- Closure: root closure waits until every admitted standalone node finishes
  or retreats. Alternatives allow these nodes to continue after root
  resolution or close immediately and leave them unfinished.
- Activity: recording uses a retained harness-command entry for the same
  session and attack, because reservations carry no session identity.
  Alternatives record all calls and filter only `status`, classify programs
  by name, or add persisted reservation ownership.
- Hook rule (a): a replay failure under a different runtime names both
  runtimes and the recorded launcher. Alternative (b) delegates to that
  runtime automatically.
- Hook rule (c): a replay failure with an unknown writer says that the
  installed controller cannot read the record. The alternative keeps the
  generic recovery message even without a known matching writer.

## Known gaps

The remaining agent-facing text updates for the skills, `SEARCH.md` and the
harness README are not written yet. The reviewer prompts also lack the
`RETRACTED` instruction. Until those prompts state the rule, only a model
that writes the marker on its own triggers recovery.
