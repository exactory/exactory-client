# Exactory 0.91.2

This release carries six tasks of two harness-improvement records: the dates of the account entries, the probe
records that a result packet delivers, the series view of a reviewer call from its start, and the documented
refusal of a foreground write while a review call commits. It follows 0.91.1. The records are
`misc/harness-improvement/20261114165500-math-conjecturer-phenomenon-run-observations` (tasks T1, T2, T4, T5 and
T7) and `misc/harness-improvement/20261115000626-reading-date-reads-a-year-the-store-never-writes` of the exactory
repository.

## What changed

The accounts of a problem value:

- `problem-value` writes `accounts_version: 2` into each new value record. A value record without the member is of
  version 1 and keeps its rules and its delivery.
- The date of an entry whose evidence is an accepted result is the day on which that result first entered a
  delivered snapshot of this store. From this release, the first delivery of a snapshot writes `recorded_at`, its
  UTC time. A snapshot that an earlier release delivered holds no `recorded_at`, so such a result gives no date.
- The date of a full reading is the local calendar day of the latest reliable update of the read version in its
  acquisition metadata. A reading whose dates are missing or contradictory gives no date, and the entry then takes
  its own `date` or `unknown`. The store no longer reads a year that it never writes.
- An entry date that names a period which contains the recording time of a candidate form does not show which came
  first. The history check now refuses such a gain with a message that says so and says how to give a time that
  decides the order, where one can. The message of the other history refusals keeps its bytes.
- A result packet of a version 2 value delivers the probe records of this store that the accounts name: the `probe`
  record and, where it is held, its `probe_intent`. The new reviewer paragraph `exactory-problem-account-probes-v1`
  says what these records are. A probe keeps its exploratory standing and enters no grade as support.

The series view and the store:

- After a reviewer call records its start, the views of the workspace render at once, without waiting for the
  render lock, so `series.json` shows the pending run from the start of its call.
- A foreground write that read its revision before a review call committed is refused with `stale_revision`, as the
  whole-store check intends. Its next step stays the same: read the current revision and run the command again. Two
  tests pin both crossings and the retry.

The texts that an agent and a reviewer read in these units were written by the project's writer and reviewed by
Astra at effort max (three parts, then two confirmations).

Incident ledger: 6 entries set to 0.91.2.

## Checks

Before the pull request, the tests of the five units, the inventory and ledger tests, and the tests that pin the
changed texts passed on Python 3.12 and 3.9, and the math-solver harness test of the delivered snapshot passed on
both. One general shard ran on 3.12 with the CI command; its only errors were five tests that start a loopback
server, which the sandbox of the lane refused, and these five passed outside it. `codex/generate.py --check`,
`git diff --check` and the release record check passed. The CI of the pull request runs the full suites on Python 3.9, 3.12 and 3.14.

## Compatibility

No file of a reviewer route's runtime identity changes, so no route becomes stale. Stored records, packets, prompts
and requests keep their meaning and their digests. A value record of version 1 validates, delivers and renders as
before, and a snapshot that an earlier release delivered keeps its bytes.
