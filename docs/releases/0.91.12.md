# Exactory 0.91.12

With this release, a command that finds a pending step of a verdict or of a submission reads the task first. It
sends a request only when the service holds none from the earlier run. A refused answer of a v7 reading turn
names the member that failed and the values that the check compared. The receipt of a v7 assignment holds one
forecast, over the inputs that remain. A guard of the test suite gives every test the same answer about the
reviewer programs of the machine. The release follows 0.91.11. Its records are
`20261120122159-verify-sends-a-verdict-again-while-its-answer-step-is-pending`,
`20261120073605-continue-submission-reads-a-member-the-server-does-not-send` and
`20261120072937-v7-reading-refusals-without-bounds-and-an-empty-unread-list` (its parts A and D), under
`misc/harness-improvement/` of the exactory repository.

## What changed

A pending step of a verdict or of a submission:

- A step of a remote operation is pending when the workspace started the request and holds no record of the
  answer. The request can be on the service, or it did not arrive.
- In 0.40.0 to 0.91.11, `exactory verify` and `exactory submit` left the managed path for a pending step. They
  sent the request directly, a second time.
- When the service held the verdict, it answered the second request with status 409 or 422, and it filed nothing.
  The text of that answer did not say that the service held the verdict. The text for status 422 said to correct
  the file and to send it again.
- When the first request did not arrive, the direct request filed the verdict. The workspace kept no receipt, and
  the step stayed pending.
- With `--managed-only`, `exactory submit` refused a pending submission step. No command sent a submission that
  did not arrive.
- Now `exactory verify`, `exactory submit` and `exactory reconcile` read the task first when a step is pending.
  For a verdict, the command reads the task while it owns the verification in the workspace. That read decides.
- A verdict goes out only when the task shows, as the current verdict of the account, the verdict that the file
  names in `supersedesVerdictId`. For a first verdict, the task must show none. This rule holds on the managed
  path and on the direct path.
- If the rule does not hold, the command sends nothing and ends with `verdict_revision_required`. Its details
  hold `verificationId`, `viewerVerdictId` and `supersedesVerdictId`.
- If the task still shows the predecessor of a pending verdict as current, the service holds no verdict from that
  request. The command then clears the step and sends the verdict.
- If the task shows a newer verdict, the command sends nothing and ends with `verdict_reconciliation_pending`.
  The task shows the ID of the current verdict and not its body. The user compares the newer verdict with the
  file on the page of the verification.
- The new option `--verdict-id` of `exactory reconcile` records the answer of such a step, and the receipt. It
  sends no request. The task must show the given ID as the current verdict of the account. That verdict must also
  be newer than the verdict that the request supersedes.
- A pending submission continues its saved intent, also with `--managed-only`. If the service shows no task of
  the record, the command clears the step and sends the request again. The service keeps one open request for a
  paper, and it answers a repeated request with that request.
- A submission reads its task by the concept DOI of the record, or by its DOI, on every path.
  `continue_submission` no longer looks for the member `verificationId` in the answer of the service, because the
  service does not send that member for a submission.
- A submission of a published record is refused with `submission_declarations_mismatch` when its
  `grandChallengeIds` or `mathProblemIds` differ from the saved submission of that record. The details hold the
  intent ID and the saved request.
- A verdict that the server refuses with status 409 or 422 gets a text that names the command to run again. That
  command reads the task and says what to do next.

A refused answer of a v7 reading turn, and the forecast of a receipt:

- The refusal `invalid_reading_response` of a v7 reading answer holds `path` in its details. `path` is a JSON
  Pointer to the member of the answer that failed. The details also hold the values that the check compared.
- Notes over the bound give `characters`, `notes_cost` and `bound` in one refusal. A list request gives `list`,
  and with it `after` and `expected_after`, or `ended`, or `rows: 0`. A passage request gives `unit` and
  `anchor`, or `requested` and `remaining`.
- A member of another type gives `expected_type` and `received_type`. An object with a missing or an extra member
  also gives `missing_fields` and `unexpected_fields`.
- The refusal notice of the replacement turn shows these values. The reviewer reads there which member to
  correct.
- A refused citation of a v7 final names its ground and its reference in `path`.
- The check accepts and refuses the same answers as in 0.91.11.
- In 0.91.11, the printed receipt of `review-assignment` of a v7 turn held two forecasts. Its stored result held
  the forecast over the inputs that remain, and the command added a forecast over the whole plan. The receipt of
  a replacement turn held only the forecast over the whole plan. `status` and the preflight report gave the
  forecast over the whole plan for every turn.
- Now the receipt of each v7 assignment holds one `capacity_forecast`, over the inputs that remain. The receipt
  of a replacement turn, recorded or checked, holds `capacity_plan` and that forecast. `status` and the preflight
  report of a v7 turn give the same forecast.
- If the harness cannot read the stored inputs of a turn, the forecast is `{status: "unavailable", is_bound:
  false, message, reason}`.

The reviewer programs in a test run:

- This part changes no command of the harness and no file of `research_harness`. It concerns a person who changes
  the source of the plugin or runs its tests, and it adds one command for that person.
- A reviewer program is the `codex` or the `claude` command-line program. Six places of the harness find one with
  `shutil.which`.
- Before this release, a test that did not state its own answer got the answer of the machine. On a machine with
  the Codex program, the lookup returned the path of that program, and a runtime reader then started `codex
  --version`. CI ran the same test without the program.
- A child process of a test read the machine in the same way. An example is `ci/record_fingerprint.py`.
- Release 0.91.4 repaired such tests in two modules. No check kept a new test from a read of the machine. On
  0.91.7, 62 tests in 15 modules read the machine, 13 of them only through a child process.
- Now `ci/unittest_shards.py` installs the guard `ci/reviewer_program_guard.py` before a test module loads. The
  CI shards of the plugin tests and the CI job of the harness tests run with the guard.
- In a run with the guard, a test gives the answer in one of three ways. It patches the lookup or a reader above
  it. Or it puts a program in a temporary directory and puts that directory on `PATH`. Or it calls
  `ci.reviewer_program_guard.use_absent_programs(self)`, and each lookup in the test process then returns `None`.
- The guard stops each other lookup of a reviewer program that reaches a directory of the machine. The test ends
  with the error `MachineReadError`. The message of the error states the repair for each case.
- A child process of a test finds a stub with the name of the program first on `PATH`. The stub records its start
  and the command of the process that started it. Then it prints a message and exits with status 127.
- The runner also fails a test that passed after a stopped lookup or a stub start. Such a test exists for three
  reasons. The code under test can catch the stop. A thread does not pass the stop on. A child process cannot
  stop the test.
- The new command `python3 ci/unittest_shards.py run-modules <name> ...` runs named test modules, classes or
  methods with the guard. Run this command in the plugin root. For the harness tests, add `--top-level-directory
  skills/math-solver/harness`.
- Eleven repairs give the 62 tests their answer. Two repairs install the runtime that the route record pins. One
  repair patches the lookup. Eight repairs call `use_absent_programs(self)`. No assertion of a test changed.

Incident ledger: 5 entries set to 0.91.12.

## Effects and limits

A pending step of a verdict or of a submission:

- `--verdict-id` records the ID that the user gives. The harness compares the ID with the task. It cannot compare
  the body, because the task shows only the ID of the current verdict.
- If the newer verdict is another verdict than the file, the step stays pending, and no command sends that file
  again. To replace the newer verdict, send a verdict file with its ID in `supersedesVerdictId`.
- Without `--managed-only`, a submission with other declarations than the saved one goes out directly, after the
  line "Managed record skipped".

A refused answer of a v7 reading turn, and the forecast of a receipt:

- A refusal notice with the path and the values is longer than a notice of 0.91.11. The harness plans a
  replacement turn with its notice. On the prototype of the design, the allowance for material of one rebuilt
  replacement turn was 316 characters smaller.
- The trial preflight that selects the form of a refusal notice keeps the forecast over the whole plan. The
  harness shows that value only when no form of the notice fits.

The reviewer programs in a test run:

- A test that looks for a reviewer program on the machine now fails in the CI shards and in `run-modules`. The
  message of the error states the repair.
- A plain `python3 -m unittest` run has no guard, with either form of module name (`tests.<module>` or
  `<module>`). The CI step that measures the coverage of `test_codex.py` has no guard either. The CI shards run
  those tests again with the guard.
- In a run without the guard, each of the 15 tests of `test_reviewer_program_guard` fails with a message that
  names the command `run-modules`. No test of that module starts a program.
- The command `run-modules` has the rules of a CI shard. Its exit status is 0 only when every named test runs and
  passes. A skipped test and an expected failure give status 1.
- A stop in a class fixture or a module fixture ends the whole run with a traceback, because `unittest` catches
  only `Exception` there. The traceback shows the lookup and the message of the error. Such a fixture cannot call
  `use_absent_programs`, which takes a test. It patches the lookup or a reader above it.
- The runner counts a read between two tests against the next test that passes. An example is a stub start in
  `setUpClass`. The traceback, or the command of the process, shows the origin of the read.
- A child process that builds its own `PATH` does not find the stub. Such a child process can still read the
  machine.
- With `use_absent_programs(self)`, a child process of the test still finds the stub. Its lookup returns the path
  of the stub and not `None`. Its runtime readers report `review_runtime_missing`, as they do without the
  program.
- A test run that a signal kills leaves its stub directory in the temporary directory. The directory holds the
  two stubs, which are two small files.

## Compatibility

A pending step of a verdict or of a submission:

- An intent with a pending step that an earlier release stored continues under the rules of this release.
- The note of 0.91.11 said that `exactory verify` sends the verdict directly while a step is pending. It told the
  user not to run the command again. That statement no longer applies. Run the command again: it reads the task
  first.
- The observation that the harness stores when it clears a submission step has the members `kind`, `locator` and
  `status`.

A refused answer of a v7 reading turn, and the forecast of a receipt:

- A stored refusal, a stored notice and a stored packet keep their bytes. A replacement turn that an earlier
  release recorded keeps its packet and its notice.
- No file that the runtime identity of a reviewer route reads changes.

The reviewer programs in a test run:

- No file of `research_harness` changes for this part. The directory `tests/` stays without `__init__.py`, so the
  harness package keeps the name `tests`.
- The function `run_shard` of `ci/unittest_shards.py` has the new required argument `take_machine_reads`.
- A branch that holds tests of its own meets the guard when it merges this release. After the merge, run the new
  and the changed test modules with `run-modules`. Give each stopped test its answer at its fixture.
- A direct run of a test module with `python3 -m unittest` still works in the plugin root, without the guard. To
  get the result of a CI shard for a module, use `run-modules`.

## Checks

The new module `tests/test_pending_remote_requests.py` (29 tests) passes on Python 3.12 and 3.9. On 0.91.11, 24
of its tests fail. The other 5 pass there, because they state behavior that does not change. The new module
`tests/test_openness_reading_v7_refusal_details.py` (21 tests) and 4 new tests of
`tests/test_openness_reading_v7_turns.py` pass on both versions. On 0.91.11, each of these 25 tests fails at an
assertion. The new module `tests/test_reviewer_program_guard.py` (15 tests) and two new tests of
`tests/test_ci_shards.py` pass on both versions. On 0.91.7, both modules fail at their import.

With the guard and with the eleven repairs, the whole suite of 0.91.7 passed through the runner on Python 3.12
and 3.9: 9,432 plugin tests in eight shards and 1,115 harness tests for each version.

After the three parts came together, each of the 206 certificates of the packet registry matched its source. The
guard of the call rows printed no difference. `codex/generate.py --check` and `git diff --check` passed.

The CI of the pull request runs the full suites on Python 3.9, 3.12 and 3.14, in eight shards for each version.
It is the first run of the whole suite of this release with the guard.

## Still to come

The parts B and C of the record of the v7 reading refusals come with 0.92.0. They tell the reviewer what the
notes cost in a request and which lists hold rows. The details of a refused argument part still reach a refusal
notice as digests. A later patch release shortens the time for which a transaction holds a lock of a large store.
Another one makes each call for a review read the context of the present.

Release 0.92.0 takes the changes of this release with its next merge of `main`.
