# Exactory 0.52.1

This release corrects two errors of 0.52.0 in the handling of a process that
ends while a lookup or a signal is in progress. It changes no record, no store
and no command output.

## A process that exits during a lookup is absent

`exactory-lab probe` identifies each process of a probe by its PID and its
kernel start identity. On Linux, the identity comes from `/proc/<pid>/stat`.
When the process exits between the open and the read of that file, Linux
answers `ESRCH` ("No such process"). Before this release, that answer ended the
lookup with a Python traceback (`ProcessLookupError`).

The post-merge test run of 0.52.0 on `main` showed the error once. It occurred
in the test of the frozen deadline, while the watchdog ended the program group.
The same code passed four other runs of the same commit.

- The lookup now reports such a process as absent. It already did so when
  `/proc/<pid>` was gone (`ENOENT`), and the Darwin lookup does so through
  `proc_pidinfo`.
- A unit test covers both answers of the kernel.

## A producer group that ended before its signal keeps the command record

The native execution of math-solver stops a command with `SIGKILL` to its
process group. This happens at a timeout, at the output limit, and at the
final wait. When the group ended between the liveness check and the signal,
the kernel answered `ESRCH`. Before this release, that error escaped, and the launcher recorded
`launch_failed` for a command that had run. The record of that command was
lost. The review of the first correction found this error. No run showed it.

- The three sites now treat `ESRCH` as a group that already ended. The command
  keeps its record and its reason (`timeout` or `output_limit`).
- Any other signalling error stays visible, as before.
- Four tests inject each case.

## Upgrade effects

None. The release changes two exception handlers and adds five tests.
