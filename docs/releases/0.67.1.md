# Exactory 0.67.1

This release resolves the items that stayed open after 0.67.0 in `misc/harness-improvement` of the exactory
repository. The openness export now checks the declaration of an openness minimum with the record-time audit's own
rules before it writes anything, `exactory-lab run` and `reconcile-run` report the execution id and the output
descriptors that `assess` needs, a problem workspace's `status` reports the literature digest that `cycle` compares,
and the agent-facing texts of 0.67.0 and 0.62.0 are corrected where an independent review found them false or
unclear. The work is recorded in `misc/harness-improvement/20261030154844-resolve-open-items-after-0-67-0`; the
new defects are the records `20261030032359-openness-export-accepts-unmatched-search-question` and
`20261030165156-cli-omits-execution-id-and-literature-digest`.

## The openness export checks the declaration

`exactory-research export --kind problem-openness` and `exactory-math search review-packet` accepted an openness
minimum whose bindings the record-time audit refuses. A whole review chain then ran on a packet that no resolved
finding passes (record `20261030032359-openness-export-accepts-unmatched-search-question`: its README counts about
6.8 million input tokens for two such chains of the unknotting record). Both exports now make the audit's declaration
checks before they write anything, with the audit's codes, through one helper that the audit calls first
(`validate_minimum_bindings` in `research_harness/openness_minimum.py`).

- The checks, in this order: the minimum's schema (`invalid_record`); the exact statement
  (`openness_statement_mismatch`); every material search of the declared formulations bound (`openness_search_stale`,
  details `search_ids`); every reading digest a record (`openness_evidence_mismatch`, details `reading_digests`); each
  binding, in the order of the minimum, with a search record (`openness_search_missing`, details `formulation` and
  `search_digest`), a formulation that is the statement or a declared neighbour (`openness_search_missing`, details
  `formulation`, `search_id` and `search_digest`) and a search that addresses it, that is, its `question` is the
  formulation's exact text or that text is one of its `queries` (`openness_statement_mismatch`, the same details); and
  every formulation bound (`openness_search_missing`, details `formulations`). The problem export still refuses an
  unknown `search_id` with `openness_search_missing` and the binding as details, now before it writes the search
  records of the earlier bindings (0.67.0 wrote them first). The native export refuses with `claim_mismatch` before
  these checks when `claim_digest` names no claim of the subject or the native state, which includes a `recovery` spec
  that carries `openness`.
- A refusal of these checks writes nothing: no evidence object, no destination and no record. The same assignment id
  can be exported again after the repair.
- `problem-openness`, `search accept` and `search complete` give the same pass or fail result for every minimum as
  0.67.0, and every recorded finding keeps its status. Two differences are visible. The refusals of these checks now
  carry the details above (0.67.0 gave `details: null`). For a minimum with several defects the first reported code
  can differ, because the declaration checks now run before the per-binding evidence, coverage, date and disposition
  checks: a first binding with a coverage gap and a second binding whose search does not address its formulation gave
  `openness_search_gap` and gives `openness_statement_mismatch`. The `cause` of a `problem_openness_stale` obligation
  can change in the same way. Obligations are computed on each read and never stored.
- A valid spec exports byte-identical artifacts. On both paths the native packet has the SHA-256 of the packet that
  0.67.0 exports from the same store, and the problem export writes the same destination tree, measured on Python
  3.12.8 and 3.9.6.
- Nothing recorded changes: no migration, no new record write, and no module that a route pins by its bytes.
- A session whose next export is refused repairs the spec, not the record. The details say what: `formulations`
  names the formulations without a bound search, `search_ids` the material searches to bind, and `formulation`,
  `search_id` and `search_digest` the binding to correct. A search addresses a formulation when its `question` is that
  formulation's exact text, character for character (for a problem statement, the whole `statement` field with its
  `---` line and details), or when that text is one of its `queries`. A new search record can reuse the captured
  responses of an earlier search and carry the new `question`, without a new capture. Then export the packet again
  under the same assignment id. The rule is stated in the math-conjecturer skill ("Openness", steps 1, 3 and 4), in
  the math-solver `SEARCH.md`, `SKILL.md` and `STUDY.md`, and in the CLI reference.

## Run output and problem status

The verification of 0.67.0 (`exactory-research/harness-dev/verify-0.67.0-v13`, findings F3 and F2) read two values
through the Python library, because no command printed them. The work is recorded in
`misc/harness-improvement/20261030165156-cli-omits-execution-id-and-literature-digest` (T1, T2).

- `exactory-lab run` and `exactory-research reconcile-run` print, beside the run summary they printed before,
  `execution_id` and `outputs`: the id of the execution that the store records for the admission after the command,
  and that record's `outputs` list unchanged, one entry `{id, requirement_id, artifact}` for each declared output
  that the run produced. A result reference of `assess` takes its `execution_id`, `output_id` and `artifact` from
  these values. Both are null when the store holds no execution for the admission after the command. A launch or a
  reconciliation whose recording fails prints `{"error": ...}` and no summary, as before.
- Nothing stored changes. The stored receipts, the run's `summary.json` under `research/runs/` and
  `experiment/results/<node>.json` keep the summary alone, and a retry with the original request id prints the same
  values. `reconcile-run --check` is unchanged.
- To find the execution, both commands read the store once more after the command. The time of that read grows
  with the store; it was not measured.
- In a problem workspace, the full `status` and `next` reports carry `literature_digest`, the value that `cycle`
  compares with a plan's `literature.literature_digest` (`literature_comparison_stale` when they differ). The
  `--summary` views do not carry it, and a study's `status` is unchanged: its digest stays at
  `preparation.literature_digest`. On the test fixture with one source, problem `status` took a median of 0.219 s
  with the change against 0.162 s before (seven runs each); the difference is the synthesis evaluation that `cycle`
  also runs. The cost on a large record is not measured.

## Corrected texts

Two independent reviews read every agent-facing text that 0.67.0 added or changed, and the 0.62.0 texts that never had
one, against the code of 0.67.0. They ran on Claude Opus 5.5 at effort max in place of the Astra review that the
Codex usage limit stopped. They found 5 major and 27 minor defects, and the release verification of `v13` found one
more limit to state. Claude Fable 5.1 wrote the corrections, 43 replacements in 16 files. The major ones:

- The hook message `Controller recovery required: DIAGNOSTIC` has two sources. When a plain `search status` still
  succeeds, the operation failed and the diagnostic names what to do; only when the status call fails too, under the
  recorded runtime, does the record need recovery.
- The Claude route's system events `init` and `thinking_tokens` are neither notices nor issues.
- The deposit skill no longer builds the sources archive at deposit time in a managed study. The command refused the
  archive that the write stage had already built and pinned, and an archive built under another name took the direct
  path without a managed receipt.
- `status` reports `draft_marker_missing` only at stage `write`. The deposit skill now says how to repair a missing or
  differing marker at the deposit stage.
- The `manuscript-review` and `manuscript-prediction` examples no longer set `author_memory_notes_present: false`,
  which states a verified absence.

The minor ones cover check mode, packet bindings, the causes of `review_context_unverified`, how a pending review
invocation ends (`review-attempt` under the run's `id`), the first reading turn that ends without output, refusal
details, `restore` and its help, the draft-marker obligation, probe examples, and the README and release note of
0.67.0 where they claimed more than that release did. The documents now also state that an HTML figure unit of a
page with a `style` element or a stylesheet link stays partial, and that a PDF capture of the same version can
complete.

## Verification of 0.67.0 on live records

With the installed 0.67.0, on read-only copies of the math-solver objectives `ferrers-hit-real-rootedness` and
`trianglefree-spectral-edit-three` (the originals were only read, and snapshots before and after are equal):
`search status` and `search next` give the state that their notes record; every recorded review authenticates,
including two Ferrers reviews bound under the local `ui_invalidate` repair of 2026-10-25; and the triangle-free
result review with its openness minimum (a 2,799,001-byte packet) reads as a chain of 26 turns whose final turn is
1,114,159 characters on the Claude route and 957,485 on a Codex route, with synthetic reviewer answers. The
reproductions of `misc/harness-improvement/v13` (full text of PubMed Central pages, PDFs served as
`binary/octet-stream` and JATS XML, figure assets, symlinked virtual environments, binary result evidence and
format-only reruns) pass with the installed 0.67.0.

## Upgrade notes

No module that a route pins by its bytes changed, so every recorded route stays valid and needs no new probe. A
session whose next openness export is refused repairs its spec as "The openness export checks the declaration"
says; recorded findings keep their status.

## Known limits

- An HTML figure reading stays partial while the page has a `style` element or a stylesheet link, because the harness
  has no CSS cascade evaluator. A PDF capture of the same version is the route to a complete figure reading.

Codex was at its usage limit for the whole release. By the owner's decision of 2026-10-30, Claude Opus 5.5 at effort
xhigh implemented, Claude Opus 5.5 at effort max reviewed the design and the texts in place of Astra, and Claude Fable
