# Exactory 0.69.1

This release makes the planning of a review turn (`review-assignment`) fast on a large store. The preparation of one
assignment now reads through one evaluation of its records view, and the request of each earlier assignment is built
once per evaluation. Every recorded value stays the same. The work is recorded in
`misc/harness-improvement/20261031165300-review-planning-rebuilds-lineage-requests` of the exactory repository.

## Why

On 2026-10-31 one planning of a problem result part turn took about 38 minutes on the unknotting record (499 review
assignments, revision 835). A profile of that planning found two causes:

- `record_assignment` gave the raw artifact store to its preparation. Each `assignment_state` and `route_state` call
  therefore started a new evaluation, and no state, request or artifact read was reused across calls.
- `build_assignment_request` ran 22,433 times for the 499 assignments. Each call rebuilt the request through
  `transport.list_built_requests` and scanned every review attempt of the store.

## What changed

- `record_assignment` binds `artifacts = Evaluation.of(records, store_artifacts)` at the start of its preparation, as
  the gate, execution-evidence and literature commands already do for their records views.
- `build_assignment_request` builds the request of a text-route assignment once per evaluation of a records view. The
  memo stores a deep copy, and each caller receives its own deep copy. A visual-route (`codex_cli_visual_v1`) request
  is built on every call, as before, because building it checks the current emitter bytes.
- The completed attempts are indexed by assignment id once per evaluation. The index reads `assignment_id` of every
  attempt, and the `status` and `request` filter applies only to the attempts of the assignment that is built, as the
  scan did before.
- The `packet` parameter of `build_assignment_request` is removed. Every caller passed the assignment's own frozen
  packet, and the function now reads that packet itself.

## Existing records

Every request, packet, prompt, digest and runtime pin stays the same. The errors stay the same for the records that
the harness writes. No route needs a new probe. The modules that a route pins by their bytes and
`review_state_evaluation.py` do not change.

On a copy of the unknotting record at revision 835, the same planning took 80.8 seconds with this release. The
assignment record and the packet bytes that it committed are identical to the ones that 0.69.0 committed on another
copy at the same revision. The commit events differ only in the runtime provenance of the operation.

records view, fit selection per view, a change of the input history, malformed attempts, a change and a restore of
the visual emitter, and one root evaluation for the preparation of a problem result part turn (15 before the change).

runs in CI.
