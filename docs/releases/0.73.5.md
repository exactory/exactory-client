# Exactory 0.73.5

This release stops failed Lean downloads from failing CI. The harness code does not change. The release follows
0.73.4. The work is recorded in `misc/harness-improvement/20261104074403-harness-problems-closed-for-good` of the
exactory repository.

## Why

CI installed Lean with `leanprover/lean-action` in all 15 test jobs of every run. The action downloads the elan
installer from GitHub and the Lean toolchain from `releases.lean-lang.org` each time, and it does not try again after
an error. In the last 200 runs, from 2026-10-24 to 2026-11-05, this step failed 18 jobs in 15 runs. The causes were
HTTP 504 errors, TLS errors, connection failures and one download that stopped for 47 minutes. A job that failed here
ran no test, and the summary jobs of every Python failed with it. For example, the CI run of 0.73.4 lost shard 3 of
Python 3.9.25 in this way.

## What changed

- Only the `checks` jobs install Lean. They run the Lean smoke test of the math-solver harness, which is the only
  test that uses Lean. No test of the `general` shards uses Lean.
- The `checks` jobs restore `~/.elan` from the GitHub Actions cache. The cache key holds a cache version (`v1`), the
  operating system and architecture of the runner, and the hash of the smoke fixture's `lean-toolchain`.
- `ci/install_lean.py` checks a restored installation. The elan programs must be executable files, and `elan`,
  `lean` and `lake` must answer `--version`. If the check fails, the script writes a warning and installs Lean again.
- Without a usable installation, the script installs elan and the toolchain in up to 4 attempts. Each attempt has a
  limit of 600 seconds. At the limit, the script stops every process of the attempt. Before each attempt, it removes
  an incomplete toolchain and the partial downloads of elan, because elan does not replace a toolchain directory that
  exists. It waits 30, 60 and 90 seconds between attempts. If every attempt fails, the job fails.
- The jobs save the cache only after the smoke fixture builds, so a failed installation is never saved. If the cache
  service fails, the jobs install Lean from the network.
- The harness tests now run through `ci/unittest_shards.py`, as the `general` shards already do. This runner fails on
  a skipped test, so a broken Lean installation cannot skip the smoke test silently. The runner has a new option,
  `--top-level-directory`.
- The regression ledger has a new entry, `ci-lean-toolchain-download`, with its tests.

No stored record changes, and no migration is necessary.

## Checks

- `test_ci_lean_install`, `test_ci_shards` and `test_incident_ledger` with the manifest, Codex, guidance and
  release-records modules: 123 tests pass on Python 3.12.8 and 3.9.6, with no skipped test. The installer tests
  run the script with fake `curl`, `sh` and `elan` programs that fail, stall or leave an incomplete toolchain, as the
  downloads did in CI.
- The harness suite, through the shard runner and through plain `unittest`: 1,030 tests on Python 3.12.8 and 3.9.6,
  with no failure and no skipped test. The Lean smoke test ran in each run. Both ways run the same tests in the same
  order.
- `codex/generate.py --check` and `git diff --check` pass.

CI on Python 3.9, 3.12 and 3.14 runs after the pull request opens. The first run on `main` after the merge fills the
cache.
