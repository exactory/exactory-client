# Exactory 0.91.13

This release ends one Python exception of `problem-value`, and it adds a command for the checks before a release.
The release follows 0.91.12. Its record is
`misc/harness-improvement/20261120203506-improvements-from-the-problem-value-cycle` of the exactory repository.

## What changed

A long chain of account entries:

- Entries of the accounts can cite each other, for example through `evidence_ids`. `problem-value` followed these
  references with a recursive function. A chain of more than approximately 1,000 entries, each citing the next,
  ended with `RecursionError`.
- The function now keeps a stack of its own. A chain of any length gets the result of a short one: the same
  evidence in the same order, the refusal `problem_account_reference_cycle` for a cycle, and the refusal
  `problem_account_reference_missing` for an unknown ID.

The checks before a release:

- `python3 ci/must_pass.py list` prints the test modules that must pass before the pull request of a release.
  `python3 ci/must_pass.py run` runs them. It starts one process for each module and each Python executable, in
  the same way as a CI shard.
- The set always holds nine modules that compare the harness with frozen values, or that pin a fixture, a version
  or a release file. `tests.test_review_request_parity` is one of them. When the diff changes the harness code or
  a fixture, four slow modules that pin the certificates of the code join them and run first.
- The set holds each changed test module. It also holds each test module that reaches a changed file of `tests/`
  through the imports between the files of `tests/`.
- For each other changed file, the set holds the test modules that import it or name it. The full suites of the
  CI cover the remaining tests.
- Release 0.91.8 was merged with a failing test. The test reaches a changed fixture builder through other test
  modules, and no list of that release held it. From the diff of 0.91.8, the command selects this test.

Incident ledger: 2 entries set to 0.91.13.

## Checks

The new test builds a chain that is longer than the recursion limit. It fails with the walk of 0.91.12, with
`RecursionError`, and it passes with this change. The new walk and the walk of 0.91.12 gave the same result on
19,916 entries of random accounts: the same evidence in the same order, and the same refusals.

`python3 ci/must_pass.py run` selected 27 test modules for this release and started them on Python 3.12 and 3.9.
At the pull request, 24 modules had passed on Python 3.12 and 8 on Python 3.9, and none had failed. The other
runs had not ended: on Python 3.12 the three slow modules `test_capacity_guard`, `test_continuity_guard` and
`test_capacity_packet_inventory`, and on Python 3.9 the modules that start after them. These runs go on after the
pull request, and the CI of the pull request runs the full suites on Python 3.9, 3.12 and 3.14.

`codex/generate.py --check` and `git diff --check` passed. The certificate digests of `capacity_packet_schema.json`
equal the source. `ci.capacity_packet_inventory --write-call-rows` reports no difference, and
`ci/series_code_reach.py --write-fixture` leaves its fixture unchanged.

The release record check reports only that 0.91.13 has no tag and no GitHub release yet. It runs again after the
tag.

## Compatibility

No reviewer prompt, packet, export or transport file differs from the release before this one, so no reviewer
route becomes stale. Stored records keep their bytes and their digests. A value record that was valid stays valid,
and its entries reach the same evidence in the same order. No payload that the release before this one accepted is
refused.

`ci/must_pass.py` is a tool for the work on the plugin. No command of a user changes.
