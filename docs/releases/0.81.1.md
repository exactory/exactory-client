# Exactory 0.81.1

This release corrects the automatic pass of 0.81.0 after the Astra 6 reviews of its code and of its texts. It follows
0.81.0 and completes phase C of the work recorded in `misc/harness-improvement/20261106085323-override-of-harness-stops`
of the exactory repository.

## Why

The reviews of 0.81.0 found three kinds of fault. The code let a pass through that the principle forbids: the same hop
twice under two gate names, and an unchecked write from a workspace that had lost its store. The code refused what the
principle permits: a gate that was already ready, and an instruction recorded for the exact write. And several
sentences of the texts disagreed with the code. Each is corrected here; the records of 0.81.0 keep their meaning.

## What changed

- One automatic hop. A `result` review of a study at `experiment`, stopped with `review_series_no_progress`, moves
  the study to `write` through `readiness` or `manuscript-readiness`. The move from `evaluate` to `deposit` is
  withdrawn: a test on a managed study shows that the publication gate cannot owe only the missing manuscript review
  while its measurement is complete. A stop of a `manuscript` review records `scope: null`, and an older stop with a
  `publication` scope is refused with `gate_override_internal_only`.
- One pass per hop. The second-pass check compares the transition, so `readiness` and then `manuscript-readiness`
  cannot pass the same move twice.
- New refusal `gate_override_gate_ready`: a gate that lists no obligation is ready, and the ordinary
  `exactory-lab state set` move applies. The messages of `gate_override_user_required` and
  `gate_override_quality_condition` name the next action, `gate-override` on the user's instruction, and invite no
  second `gate-auto-pass`.
- Public writes after an automatic pass. `submit` and `verify` accept an instruction recorded for their exact action
  on the managed path too. The managed path of `deposit` admits an instruction of the gate `publication` or any
  action-scoped instruction, and each Zenodo write then checks its `METHOD` and URL path, for example
  `POST /api/deposit/depositions`; an instruction of the gate `publication` keeps covering every Zenodo write. The
  guard finds `.exactory/automatic-passes/` itself, from the current directory up to the nearest workspace root, so a
  workspace that lost its store is checked and a nested independent workspace is not bound. A refusal on a managed
  path leaves no pending remote step: the intent keeps a `local_authority_refusal` observation, and the same command
  resumes it once the instruction is recorded.
- `review-series`. A failure to record a terminal stop never changes the stop, its class or the exit status; a result
  packet that is not JSON no longer turns the stop into `exit 1` with `input_io`. A recorded stop reports
  `revision_after_stop`. The `retry` field of a stop record is null except for `review_series_no_progress`.
- The deposit description of an automatic pass is a paragraph for a reader of the paper: which check, which stop,
  that the harness classified the stop as its own defect and proposed advancing the work without the missing
  reviews, whether the stored record confirms the move, and that the entry supplies no review approval or permission
  to publish.
- `exactory-research example gate-auto-pass` reads the examples file like every other command.
- PENDING fix-3: the waiting list.
- The texts (`docs/research-workflow.md`, "Stops and overrides"; `docs/research-cli.md`; the skills) follow the code:
  the class of a stop whose record failed, the parking rule, the recovery after `stale_revision`, the attachment of a
  record to a problem as a write of `exactory`, the file names under `final/overrides/`, and the record inventories.

## What stays the same

- Records written by earlier releases do not change, and no migration is necessary. A user override written by
  0.80.0 reads back unchanged; a frozen fixture of the released writer checks it.
- A workspace without `.exactory/automatic-passes/` sends its public writes as before, including the direct path
  after a transient store error.
- The retry schedules and the stored attempt classifications are unchanged; the seventh provider failure still ends
  in a stop.
- The metadata of a deposit without an automatic entry is byte for byte the same as in 0.80.0.
- PENDING fix-3: how a user override with a `public_action` appears in the deposit disclosure.

## Known limits

- A store that holds an automatic `gate_override` needs 0.81.0 or later. The released 0.80.0 opens such a store and
  takes a snapshot, but its `exactory-research status` fails with `KeyError: 'instruction'`.
- PENDING fix-3: the `gate_override_retry_pending` row of the refusal table, and the retry of a stop record that
  could not be written.
- The exact `public_action` has no origin component.
- The public-write guard reads the workspace from the current directory; a command run outside the workspace tree is
  not checked.
