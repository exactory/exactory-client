# Exactory 0.52.0

This release changes how AI Science and math-solver studies move forward. The
research actions become tools that a study can use at any stage, in any order,
with amounts that each call states. Each orchestration keeps the gates that its
claims must pass. Independent assessment stays a condition of each claim.

## Research tools at any stage

The `cohort`, `literature-review`, `ideate` and `experiment` skills are tools.
A study can call them at any stage. The new [tool catalog](../research-tools.md)
lists every tool, its arguments, the commands that do the work and what each
call records.

A tool call grants no approval. A claim is ready only when its fixed minimum of
evidence and its independent assessment are complete. The preparation policies
(`lineage-v1`, `sampled-v1`, `exhaustive-v1` and `screened-v1`) stay as presets
of the default amounts.

## The depth plan

`exactory-research depth` records a depth plan for a research study, with a
reason. The plan sets the default amounts of the bounded tools:

| Amount | Default |
| --- | ---: |
| `loop_abstracts` | 100 |
| `round_loop_abstracts` | 40 |
| `hits_per_query` | 10 |
| `innovation_candidates` | 10 |
| `innovation_cases` | 5 |
| `sample_size` | 100 |
| `search_readings` | 20 |
| `core_fulltexts` | 10 |

Each search, loop or search-hit reading batch, sample, core full-text
requirement, innovation section and loop closure accepts a `depth` object for
one call. The record keeps the effective amounts of the call. A record is
judged by its own recorded amounts, never by a later default. Amounts are
positive integers. The budgets still bound the cost.

A depth plan changes amounts of work. It never changes a claim minimum. The plan
stays outside the configuration and every dependency digest. Verification
keeps its fixed amounts and refuses a plan or an override with
`profile_inapplicable`.

Under `exhaustive-v1` and `screened-v1`, a new innovation section needs at least
`innovation_cases` external cases and at most the larger of ten and
`innovation_cases`. With the defaults, this is the earlier rule of five to ten.

## Exploratory computation (`exactory-lab probe`)

`exactory-lab probe` runs a quick calculation at any stage, also before a
target or a cycle exists. It pins the script and the inputs, records a
`probe-intent` and holds the timeout against the `experiment` time budget. Then
it runs the script in a new directory under `research/probes/ID/`. The `probe`
outcome records the outputs, both streams, the exit status and the measured
time.

- One probe ID runs once. A retry while the probe runs returns
  `{"status":"pending"}` and does not start a second run. A retry after the end
  returns the original receipt.
- If the worker process stops, the program can continue. A watchdog process
  enforces the frozen deadline: it stops the recorded process group, makes sure
  that the group is gone, and records `timed_out`. A retry after the deadline
  records the outcome. Before the deadline, a retry returns `pending`.
- An intent with no outcome releases its time hold only after the run is known
  to be over. The absence of an outcome alone never releases it.
- Probe outputs keep an exploratory origin through later imports and pins. They
  give no execution or result credit. An admitted cycle that produces the same
  bytes earns credit only through its own observed run.

## Search coverage and provisional searches

Each new search records one `coverage` entry per query. The entry holds the
requested and returned counts, the inspected count and the captured page
positions. It also holds the provider, the ordering of the captured request,
and a kind. The kind is `complete` only with enumeration evidence, `top_k` only
with ordering evidence, and `bounded_unordered` otherwise. An author label
cannot set the kind. Older searches derive their coverage from their saved
evidence, or report `unspecified`.

Each new search also records `integrity_errors`: parser and capture errors,
apart from bounded enumeration. For a research study, a bounded search is
valid when it has no integrity error. Verification keeps its earlier rule for
incomplete enumeration.

A search can record a provisional `question` before the literature scope
(roots) exists. It appears in `status` under `provisional_searches` and counts
for no claim. A later scoped search can reuse its captured responses through a
recorded `binding`.

## The direction gate of AI Science

The `literature` stage ends at the new `direction` gate. The gate is ready when
the configuration is ready and the selected research decision is ready at the
`cycle` boundary. Before any decision exists, the gate lists the missing
direction evidence, and `next` names it.

The direction needs this minimum of evidence:

1. A `direct` search bound to the current literature scope
   (`direction_search_missing`). The search has bounded or complete coverage, a
   disposition for every captured result and no integrity error
   (`direction_search_incomplete`).
2. A full reading of every work that the search judged relevant or
   contradictory, and of every root (`direction_reading_missing`,
   `direction_root_reading_missing`). A source deferral leaves the reading
   missing.
3. A selected `standards` section whose sources are valid and whose
   applicability has no open finding (`direction_standards_missing`,
   `direction_standards_unresolved`). Staleness by the foundation, the
   configuration or the constitution alone does not count.
4. A current Grand Challenge record (`grand_challenge_missing`).

New decisions carry `gate_version: 2`. An `investigate` or `pivot` decision is
refused while the minimum is not met. The decision stores the digest of the
decisive evidence (`direction_evidence_digest`) and stays ready only while the
minimum holds with that evidence. New decisive evidence, such as a new direct
search or a replaced standards section, needs a new decision with reviews that
received it. Target commitment follows the same rule.

## The Q1 bar

The bar review states four things. It names the field and the Q1 venues. It
states the advance over the closest prior work that such a venue accepts for
this intent. It states the evidence standard that the venue requires. It states
the conditions that make a result unpublishable there. The candidate stays
hidden from the bar.

The new assurance `q1_venue` is assessed as potential in slate reviews and as a
realized, supported advance in result reviews. For a `gate_version: 2`
decision, `investigate`, `pivot` and `develop_manuscript` need `q1_venue` passed
in both reviews. An authorized `deliver_requested` keeps its stop checks and its
authority and quality conditions. Assignments made with the earlier prompts
still record under the earlier assurance set. The new prompts use the template
id `exactory-q1-review-v2`.

## math-solver

math-solver is an orchestration over the same tools. Its gates are the original
contract, an openness finding, independent proof acceptance, formal
verification when requested, and a closure that covers every deliverable.

- A `role: research` proposal can carry `foundation: null`. Common preparation
  is optional for native research, and a changed common preparation no longer
  blocks fresh native work. A recorded foundation stays validated by its
  recorded digests and pinned bytes. Verification keeps every foundation audit.
- An append-only `review_workspace_recorded` event names the common workspace
  that holds the review assignments.
- New result acceptances and root closures use a version 2 review with an
  `openness` finding. The finding is `supported_open`, `already_solved` or
  `unresolved`. It is bound to the exact statement, with its evidence, search
  date and coverage.
- A `supported_open` or `already_solved` finding carries a pinned minimum. The
  minimum names the exact statement and its declared neighbouring formulations.
  It binds one common search per formulation, with coverage and a capture date.
  It binds the full readings of every relevant, contradictory or settling
  result, and the settling work for `already_solved`. The harness checks the
  minimum against the common store that the objective is associated with. An
  unavailable, deferred or unresolved source is a gap, which allows only
  `unresolved`. A hit that a later search resolved as out of scope needs no
  reading. A duplicate names its canonical source, which needs a full reading.
  The review packet delivers the search records, the captured responses and
  the source bundles. The refusal codes start with `openness_`.
- Root closure needs `supported_open` or `already_solved` for every objective,
  also for a request to prove or disprove the proposition. `already_solved`
  keeps requested formal verification and every other deliverable. A new native
  checkpoint after a closure opens the openness review again.
- No Grand Challenge record is necessary for a mathematical objective.
- `plan` validates the complete `problem.json` and the inputs that it reads. It
  no longer needs `study/problem.md`.
- Exploratory calculations use `exactory-lab probe` in the common workspace and
  give no proof credit. Every calculation that a decision, proof, finite check,
  counterexample or acceptance relies on still needs native admission. A
  native import keeps the probe origin of its bytes, also through a JSON
  wrapper, a renamed artifact or a review-packet export. A fresh checkpoint,
  acceptance, closure or reassessment refuses such bytes as proof,
  counterexample or decision evidence (`exploratory_evidence`). The cash-out
  inventory lists every probe that the attack used.
- Version 1 acceptances and closures replay unchanged.

## Direction review coverage

Both observed reviews of a new direction decision must have received the
decisive evidence. Coverage counts only content that reached the reviewer:

- the exact captured source text attached to an observed packet, or
- checked passages that together cover every inspected range of the reading,
  and every image that an inspection names. Each passage is matched against
  the captured bytes and its provenance.

New slate and result packets and their supplements deliver these passages in
chunks of at most 2000 characters. They also deliver the checked original of an
inspected PDF and the named images. Reading records, artifact descriptors,
inventory membership and recording dates give no credit. Existing packets count
only the content that they actually delivered. A decision whose reviews lack
the content needs an observed supplement. The author's readings are never
repeated. `status`, `next` and `gate` compute this without writing to the
store.

## Claims stay current after unrelated changes

A plan, an admission, an assessment and a checkpoint bind their claim
dependencies. So do a readiness candidate, a readiness review, a support
decision and a scoped publication contract. The claim dependencies are:

- the objective, the scope and the assumptions,
- the plan and the executions,
- the evidence, the readings that it uses, their bundles and the source
  records that they name,
- the inheritance, the validations, the strategy failures and the
  authorizations.

The preparation digest, the configuration digest, the constitution and the
synthesis sections stay in the recorded dependency maps for audit. A change of
them alone no longer makes a claim stale. A later reading of a cited paper that
the claim does not use leaves the claim current too.

A record that an earlier release wrote keeps its digest. The harness checks
that digest against the record's recorded inputs, then compares the claim
projection of those inputs with the current one. A candidate that a review
bound only by its hash is rebuilt from the records at the review's recorded
revision, never from current values. An input that cannot be rebuilt gives
`claim_reassessment_required`, which names the record.

Managed research studies move from `initiate` to `literature` directly and
leave `cohort` without a gate. They enter `ideate` through the `direction`
gate, also when they return from `experiment`. They return from `evaluate` to
`literature` on an approved `investigate` or `pivot` decision. `status` and
`next` follow the current milestone. The preparation report stays in `status`
as advisory.

## Upgrade behavior

The research constitution becomes Version 7. A study that adopted Version 6
keeps it. Its configuration, foundation and synthesis reports and digests stay
byte-identical, with no revalidation obligation, so native audits that
recompute them pass. A research study adopts Version 7 with `constitution` and
the previous SHA-256, as after earlier releases. Adoption alone changes no
claim. Verification workspaces keep Version 6.

These effects were measured with `exactory-research status` on copies of 14
stores on the maintainers' machine. The stores are nine studies, four
verifications and one test store. Each was read with 0.50.1 and with this
release:

- The four verification stores and the test store report the same obligations.
- In every research study, the obligations that unrelated changes caused are
  gone. These are `synthesis_dependencies_stale`,
  `development_dependencies_stale`, `inherited_result_stale`,
  `inheritance_refresh_stale`, `candidate_checkpoint_stale`,
  `readiness_review_stale`, `novelty_comparison_stale` and
  `publication_scope_stale`, and the `branch_resolution_unverified` entries
  that followed from them.
- Two studies report `claim_reassessment_required` for one readiness review
  each. The review bound a candidate composition that 0.50.1 cannot rebuild
  either. 0.50.1 reported the review as stale.
- One study at `evaluate` with a pinned manuscript reports
  `publication_readiness_stale`: a claim dependency of the pinned candidate
  changed after the pin. 0.50.1 reported `publication_scope_stale` for the same
  study.
- In a managed study before `ideate`, `status` lists the obligations of the
  `direction` gate. The obligations of the preparation report, such as
  unread cohort abstracts and unresolved references, move to `preparation`
  as advisory, and `next` names the direction evidence.
- The remaining obligations of each study are unchanged.
- Verification stores read faster than with 0.50.1. A study with recorded
  reviews reads slower, because the harness rebuilds the candidate at each
  recorded review revision. On the three largest studies, `status` took 1.2
  to 1.4 times the 0.50.1 time in paired runs. Peak memory stayed between
  0.97 and 1.13 times.

New obligations apply at the next commitment. The direction minimum and the
`q1_venue` assurance apply at the next `investigate` or `pivot` decision. The
openness minimum applies at the next native result acceptance or closure.
Pending executions reconcile once under their frozen authority. An already
admitted cycle finishes and keeps its evidence.

## Validation

The test record is `docs/testing/tools-and-orchestration.md`. In short:

- GitHub Actions runs the complete suite on Python 3.9, 3.12 and 3.14 for
  the head of the pull request to main. The run is on the pull request
  page. Earlier runs on the integration branch found one fixture gap and
  nine tests that assumed the Version 6 constitution. All were fixed before
  the final head.
- The math-solver harness suite alone passed on Python 3.9 and 3.12 (810 tests).
- Each slice passed its own modules on Python 3.9 and 3.12 before its merge,
  as the commit messages state.
- Astra (gpt-6-astra at effort xhigh) reviewed the design in four rounds and
  the code in two rounds. Every finding is fixed in code.
- `exactory-research status` ran on copies of 14 recorded stores with 0.50.1
  and with this release (the table in the test record).

## Known limitations

- Verification keeps constitution Version 6 and its fixed amounts. The
  verify, grand-challenge and math-conjecturer orchestrations are not yet
  converted.
- Exploratory computation for a managed mathematical objective runs as an
  `exactory-lab probe` outside native admission. Whether it must pass native
  admission instead is open for the user.
- Whether problem creation extends `math-conjecturer` or becomes its own
  orchestration is open for the user.
- `status` of a large study store stays costly. On the largest local store
  (4.1 GB) it took about five minutes and 13 GB of memory. A study with a
  legacy readiness review, a scoped review and a pinned manuscript takes up
  to about 1.4 times the 0.50.1 time. The candidate, the synthesis and the
  foundation are rebuilt once at each recorded review revision.
- A slate packet attaches the checked original of every inspected PDF, so a
  direction with many PDF readings gives a large packet.
- Tests with short run timeouts or fixed time windows can fail on a heavily
  loaded machine, as in earlier releases.
