## Recommended scope

Complete the existing controller, then include a small deterministic hardening
layer in the same local release before the final skill alignment and release
validation. Keep one authoritative obligation graph, event log, account system
and executor. Do not add a competing job registry or silently weaken native stages.

The priority is to stop an admitted but strategically empty computation before
launch, and to make its actual result constrain the next action. Exact evidence,
user control and an honest progress view remain separate authorities.

## 1. Finite domain and completeness

Replace prose-only finite-domain declarations with a closed record, reusing
existing case/interval scope forms where possible. A bounded encoding references
its immutable encoding and a reviewed finite-size bound. The admission binds
the exact domain and completeness basis, not merely the label `finite_proof`.

Distinguish three claims:

- A finite proof settles an exact finite obligation. If it contributes to an
  unbounded root, the separate quantified bridge remains explicit.
- A bounded diagnostic decides a named strategy question. Its omission consequence,
  possible outcomes and route changes need independent review.
- A bounded counterexample search may resolve an existential target on success;
  failure over its bounded domain does not refute an unbounded existence claim.

A proposed bridge need not already be proved before research starts. However,
no finite result closes the broader obligation until the required bridge is
accepted. A prefix cannot obtain universal finite-proof authority from approving
prose alone. Native checking of an already produced exact proof retains its
separate, input-reviewed verification contract.
In particular, listing a finite prefix and an unproved infinite tail as two
premises does not itself justify a prefix-computation branch. Such a branch needs
a verified reduction leaving that finite residue, a genuinely decision-guiding
diagnostic admission, or the existing independent standalone-significance basis.
This requirement does not forbid investigating a substantive proposed bridge or
uniform lemma before that bridge has been proved.

## 2. Information-value preflight

Bind a small structured preflight to each admitted computational question:
the unresolved uncertainty, existing evidence digests examined, facts already
determined, outcome-specific next actions, the cheapest sufficient check and
the failure/retreat condition. Independent admission must assess these fields.

When existing results determine a proposed weaker bound or an average of identical
certified values, the default action is to reuse that evidence, not allocate a new
solver job. A genuinely different question on the same data remains admissible.
Unchanged authorized retries consume their original allowance without requiring
a newly invented significance review for every invocation.

The mechanism checks record presence, identity, scope and review binding. It does
not claim to decide arbitrary mathematical information value by comparing strings.

## 3. Result interpretation before further computation

After a finite run, require one immutable interpretation linked to its actual run
and evidence digest. It selects a predeclared outcome or explicitly records an
inconclusive result, the decision made for the root route (possibly none), the
remaining obligations and the next authorized action.

An unclassified result puts interpretation/reconciliation ahead of a new run.
Timeout, UNKNOWN, a no-hit prefix and a successful audit of a log do not become
feasibility results or theorem proofs. Interpretation alone grants no proof credit,
new account segment, new branch or new execution authority. Changed mathematical
scope still requires the ordinary reviewed amendment.

## 4. Verification design and honest resource records

Before an expensive producer, bind its certificate shape, independent checker
method, expected producer/checker cost, hard checker cap and fallback design to
the admitted task. A checker that must rediscover the original hard result is a
reason to redesign the certificate, not to run without a bound. Replay, core and
case-split certificates are examples, not mandatory formats for every theorem.

Retain the existing external deadline, command-unit accounting and single owned
workload. Add measured elapsed execution time and distinct producer/checker roles
to run provenance. Report unobserved CPU time, memory, internal solver calls and
transport retries as unknown. Do not present reserved accounting as measurement.
Bound local snapshot bytes before materializing them, with a declared total limit
and bounded reads. Current capture reads entire files before storing them; a huge
certificate must not exhaust memory merely during preflight. Stream hashes for
large read-only dependencies, without describing this as a runtime memory sandbox.

Add a tiny adversarial test with ignored cooperative interruption. Preserve
ownership-safe recovery and do not introduce a full OS sandbox or a global CPU
allocator across unrelated projects.

## 5. Pause, local review and aggregation

The current hook task fixes Stop accounting while a workload is pending and makes
all lifecycle paths consult the same durable pause. Questions, compaction and
false/missing hook flags do not authorize resume.

Specify the distinction between pausing future work and cancelling an already
owned workload. An explicit cancellation option must use the existing launcher
ownership channel, retain charges and record acknowledgement; an uncertain PID
must never be signalled. This is an additional API, not current pause behavior.

For local packages, use typed review/resolution receipts tied to exact claims,
proofs, drafts and dependencies. Reuse existing review primitives where possible.
Keep mathematical validity, paper-quality evaluation and novelty distinct; do not
parse free-text FAIL or unresolved novelty into a guessed semantic verdict.
Structural native finish alone remains insufficient for verified mathematical
completion. Preserve old native journal and parent formats.

Test the reported three-extraction/two-completed-children aggregation state.
Already proved linking uses existing administrative acceptance/completion; a new
deduction needs a lawful admitted move and its actual allowance. The result must
be a concrete legal next step or an exact unmet condition, not a fourth extraction,
fake stall, or renamed budget. Prefer a checkpoint successor with inherited usage
to any generic `precedes` override.

## 6. Evidence-only cash-out and progress report

Cash-out must identify the admitted covered obligation or independently admitted
standalone mathematical claim supporting each proposed unit. A prefix or pipeline
without either basis remains evidence. A genuine independently significant finite
theorem remains eligible; finite does not mean unimportant.

Implement the requested parent `PROGRESS.md` using the ownership, append-only
history, mutable current-tree region and recovery rules in the existing progress
addendum. Each significant update has three to five English lines. Use exact
obligations, domains, review levels, cash-out state and next decisions.

In light of the retrospectives, the proposed default is justified case coverage
only, with its denominator and missing common obligations. Overall progress on an
unbounded theorem is `not quantifiable` unless the exact contract is resolved.
Do not infer percentages from jobs, checkpoints, pages, schemas or file counts.
Only audited root proof completion receives the proof-complete label of 100%;
disproof remains explicitly labelled disproof. No subjective estimate is proposed
for this release.

## Deliberately separate follow-ups

A cross-provider source cache/cooldown/request ledger and a lighter analytical
workflow merit separate small designs after the controls above. They require
retrieval-connector visibility and revised study/applicability contracts. Do not
claim to enforce hidden MCP retries, duplicate source requests outside the observed
boundary, or in-context reasoning. Existing study and admission requirements remain
binding until their replacements are explicitly approved.

The same applies to an OS-level memory/disk sandbox or generalized ordering
overrides. These are not needed to justify the current hardening and must not
silently enlarge it.

## Validation and delivery

Preserve approved task evidence. Add genuine RED/GREEN tests for new contracts,
then fresh independent scope/quality review and the final whole-branch review.
Extend the prewritten behavioral scenarios for predetermined averages, implied
bounds, missing completeness, expensive checker rediscovery, UNKNOWN/log audits,
and evidence-only publication pressure. Keep valid necessary-diagnostic and
standalone-result controls so the gate does not become a blanket prohibition.
